## 二、索引 key 到底长什么样

```
主键记录  [表ID 4B][索引ID=0 4B][主键值保序编码]              + 版本段(BE 追加)
二级索引  [表ID 4B][索引ID≥1 4B][索引列值保序编码][主键值保序编码] + 版本段
唯一索引  [表ID 4B][索引ID≥1 4B][索引列值保序编码]              + 版本段   ← 故意不含主键
```

三件事必须记住:

1. **索引 ID 每表独立、从 1 起、不复用**(`Catalog.nextIndexIds`,计数器 `sys_counters` 的 `next_index_id:<table_id>`)。
2. **唯一索引的用户键里没有主键** → 两个事务插同一个列值,写的是**同一个用户键** → 直接落到 P3 已验的写写冲突上。唯一性不是新协议给的,是复用。
3. 唯一索引的 **value 存主键编码**(回表与冲突报错要用),二级索引 value 为空。

## 三、链路一:INSERT 时索引怎么跟着写

```
Cli/协议 → SqlEngine.execute → Parser → Executor.insert:370
   ├─ 主键记录 + 每条 ACTIVE/BUILDING 索引记录 → 同一个「有序 KV 列表」
   │    · IndexCodec.entryKey:57(索引列值 + 主键值)
   │    · 唯一索引先查重:同快照下存在且非墓碑 → 抛 1062(错误信息带索引名/列/值/已有主键)
   └─ 交给事务写集 → CommitTxn 一次批记录(WAL → fsync → memtable,顺序不变)
```

要点:**索引记录与主键记录同一个 `commit_ts`**,所以按快照读时**必然同生同灭**(场景 5)。

## 四、链路二:一条走索引的 SELECT

```
Planner.access → Plan(Kind.INDEX_POINT / INDEX_RANGE)
   ↓
Executor.forEachMatch:1080 → forEachIndexMatch:1080+
   ① 在读视图上扫索引区间(用户键级,IndexCodec.equalityStart/lowerBound…)
   ② 每个索引项解出「列值 + 主键值」
   ③ 按**同一快照**点查主键行
   ④ 墓碑 → 跳过
   ⑤ **二次校验**(:1115,FR-501):行的该列值必须等于索引项里的值,不等 → 跳过
   ⑥ 残余谓词过滤 → 输出
```

**第 ⑤ 步是本期最容易漏、也最容易出"幽灵行"的地方**:改了索引列后旧索引项的墓碑可能还没回收,索引项存在 ≠ 这行现在还是这个值。

## 五、链路三:CREATE INDEX 的回填(本期最"重"的一段)

```
Catalog.createIndex:472 → 写 sys_indexes 一行,state = BUILDING(不可用)
   ↓
Executor.backfill:518
   循环:扫一批(默认 index_backfill_batch=1000 行)→ 本批索引记录独立提交
        → 更新 build_cursor(IndexCodec 主键编码的十六进制,FR-468)
   ↓
全部完成 → Catalog.updateIndexState(ACTIVE)   ← 这条记录最后写(对外承诺不可逆)
   期间若发现唯一值重复 → state = DROPPED 并报出重复值与前两个主键
```

- **回填期间的新写入也进索引**(I16 拍板 A):所以转 `ACTIVE` 前**不需要**再补扫增量。
- 中途被强杀 → 重启后仍是 `BUILDING`(游标在系统表里)→ 重跑同一条 `CREATE INDEX` 从游标续做。
- `BUILDING` 期间查询**退化全表扫且不报错**(K88)。

## 七、这份代码的坑(读的时候会绊到)

1. **全表扫必须跳过索引项**。索引记录和行记录在同一张表前缀下,只靠 4 字节索引 ID 区分 —— `Executor` 里用 `KeyCodec.indexId(key) != INDEX_ID_PRIMARY → continue`。漏了它,全表扫会把索引项当数据行。
2. **索引用户键不含版本段**,BE 返回值要 `KeyCodec.userKey()` 剥 8 字节。客户端层还加了 key 长度校验,否则异常会被兜成 `1105`(内部错误),查起来极难。
3. **唯一索引的 key 绝不能带主键**,否则并发唯一性立刻失效(两个事务写的是不同 key,写写冲突不会触发)。
4. **二次校验不能省**(见 §四 第 ⑤ 步),否则 `UPDATE` 改索引列后旧值查出幽灵行。
5. **`ACTIVE` 那条记录必须最后写**。先把状态改成可用再回填,等于对外承诺了一个半成品索引。
6. **回填游标要落盘**(`sys_indexes.build_cursor`),只在内存里等于崩溃就要从头扫。
7. 测试脚本会 `taskkill` 所有 `be.exe`/`fed` —— **不要和别的会话(尤其编码 agent)同时跑**;而且这些脚本用固定端口(9900/9906/9991、9600/9691、9800/9806),上一次跑残留的进程会直接让下一轮全红(本次核验就踩了:**端口未释放 → BE 绑不上 → 一连串"无法连接 BE"**)。

## 八、建议的阅读顺序(约 50 分钟)

1. `storage/IndexMeta.java` + `storage/IndexCodec.java` —— 先把 key 形状吃透。
2. `catalog/Catalog.java` 的 `createIndex/dropIndex/updateIndexState/updateBuildCursor` —— 元数据与状态机。
3. `execute/Executor.java` 的 `insert/update/delete`(索引维护)→ `forEachIndexMatch`(读+二次校验)→ `backfill`(回填)。
4. `planner/Planner.java` 的索引选择 + `Plan` 的新 Kind。
5. `execute/MetaCommands.java`(SHOW 与虚拟表,量大但都是模板代码)。
6. `scripts/tests/p4-test.sh` 的 SC-319~SC-341 分段,对着代码把断言验一遍。
