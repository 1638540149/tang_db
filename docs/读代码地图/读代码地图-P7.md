# 读代码地图 · P7(增量:向量这一跳怎么走)

> 本期新增的能力只有一条主线:**向量列怎么写进去、图段怎么长在 segment 上、一次 top-k 检索怎么从 FE 走到 BE 再回来**。
> 读之前先记住两条红线:**BE 不认识"列""类型"这种概念**(只认「定长 float32 槽 + 维度 + 度量操作码」);**FE 不碰 BE 的数据目录**(所以图段只能由 BE 自己写)。

## 一句话

写:`INSERT ... ai_embed(text)` → FE 按批调外部模型 → 向量作为定长槽写进行 → WAL → memtable → segment;
查:`ORDER BY l2_distance(col,'[…]') LIMIT k` → FE 规划(选路径 A/B/精确)→ 每段图检索出 top-ef → 归并 + MVCC 过滤 → 不够 k 就翻倍 ef → 回 FE 打分/还原结果。

## 主链路

### A. 向量化入库

```
SQL INSERT ... SELECT ai_embed(content) ...
  └─ FE: ai/AiService.embedAll (:160)     按批(默认 1024)→ embedBatch (:238) 调端点
         ├─ 幂等键 = hash(模型版本 + 维度 + 规范化文本) → LRU 命中直接复用
         └─ 校验维度/NaN → 失败整批不写
  └─ FE: 普通 INSERT 路径写行,向量列按 VECTOR_FIXED 槽(4×n 字节)编码
  └─ BE: WAL → memtable(与其它列同一条批记录)
```

### B. 图段(segment 的伴生文件)

```
segment 落盘(flush / compaction)
  └─ BE: store/vector.go buildVectorGraph
        ├─ 读该 segment 的向量槽 → [][]float32
        ├─ vecidx/build.go Build (:34)   自研 HNSW:分层 + greedy + 束搜索
        ├─ vecidx/codec.go WriteFile (:14) 写 <seg>.hnsw → fsync
        └─ MANIFEST 记 vec_indexes[segment] → 才可见(FR-746)
启动:vecidx/codec.go ReadFile (:101) + Graph.Check (:68) 校验 nodeCount/校验和,
      不匹配 → markPending(待重建)该段退化为暴力,后台补建
```

### C. 一次向量检索

```
FE QueryEngine.vectorPlan (:3264)      判定:有没有向量 ORDER BY、是否可下推、路径 A/B/精确
 ├─ 精确:runVectorExact (:3603)        全表取向量 → FE 算距离 → 排序取 k
 ├─ 路径 A:runVectorPathA              结构化谓词先算 → 允许集 → 在允许集内打分(本期实现)
 └─ 路径 B:ANN
      └─ BE server.SearchVectorIndex (server/vector.go:65)
            └─ store.SearchVectorIndex (store/vector.go:525)
                  ├─ 每段:vecidx/search.go Search (:21)  图内束搜索(ef、按距离)
                  ├─ memtable:暴力(未建图)
                  ├─ 归并 top-k + MVCC 可见性过滤
                  └─ 不足 k → ef 翻倍重试(上限 ef_max);预算尽 → 回退暴力或标 partial
      └─ 回 FE:取候选行 → 精确打分排序 → 结果自描述(approximate/ef_used/candidates_examined/partial)
```

## 与本期的边界(读代码时最容易怀疑的地方)

1. **BE 侧确实出现了"向量"字样** —— 这是本期唯一一次让 BE 接触数值语义:它拿到的是 FE 下发的「定长 float32 槽 + 维度 + 度量操作码」,不认识列名/类型名。判定红线时看这一点,不要看有没有 `vector` 这个词。
2. **路径 A 没有走图**:实现是"先物化允许集 → 在允许集内精确打分"(验收报告 §7 记为偏差)。结果对,但没有图检索收益。
3. **召回矩阵规模很小**(1,500 行 × 8 维),全 1.0 不能外推;真实规模(10 万 × 128 维)的时延实测 613ms,门限 100ms,未达标。
4. **memtable 永远暴力**:新写入的向量不建图(K163),批量导入刚结束时检索会全走暴力,看起来"越查越慢"是正常的。
5. **图段与 segment 同生命周期**:删表/compaction 后旧 `.hnsw` 必须消失;`SHOW VECTOR INDEXES` 的 `pending_segments` 不为 0 时该段检索退化为暴力。

## 读这一期建议的顺序

1. `fe/.../storage/VectorValues.java`(最短,看清字面量与三个距离函数)
2. `be/internal/vecidx/codec.go`(图文件长什么样,先看格式再看算法)
3. `be/internal/vecidx/search.go`(束搜索,100 行级)
4. `be/internal/store/vector.go` 的 `buildVectorGraph` 与 `SearchVectorIndex`(生命周期与归并)
5. `fe/.../query/QueryEngine.java:3264~3620`(`vectorPlan` 三种路径怎么选)
6. `fe/.../ai/AiService.java`(批量、幂等、失败语义)
