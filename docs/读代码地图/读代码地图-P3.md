## 二、BE 侧:MVCC 是怎么落地的

`be/internal/store/mvcc.go` 只有 269 行,但它定了整期的物理约定。

**① key 布局:用户键 + 8 字节版本段**

```
AppendVersion(userKey, commitTS) -> fullKey     // 追加版本段
SplitVersion(fullKey) -> userKey, commitTS      // 拆出用户键与版本
```

版本段用 **`^commit_ts`(按位取反)倒序** 存放。这不是花活,是让下面三件事**变成读第一条**:

- 读最新版本 = 读第一条
- 按快照读 = 从前往后找第一条"版本 ≤ 快照"的
- 范围扫描时,每个用户键的旧版本自然被跳过

**② 快照读**

```
Engine.GetSnapshot(userKey, snapshot)   // 对外
  └ getSnapshot(...)                    // 逐版本往前找可见的那条
Engine.latestVersionTS(userKey)         // 找该用户键的最新版本号(冲突检测要用)
Engine.MaxCommittedTS()                 // 取号水位(BeginTxn 返回给 FE 当快照)
```

**③ 扫描器**

```
Engine.NewMVCCScanner(start, end, snapshot, limit)
  └ MVCCScanner.Next()   // 按用户键分组,每个用户键只吐"对快照可见"的那一条
  └ prefixUpperBound(key) // 圈"以某用户键为前缀的原始区间"(点查/冲突检测靠它)
```

**⚠️ I7 的坑就在这里**:`prefixUpperBound` 这类"按原始字节圈区间"的做法,在**用户键互为前缀**时(`key-1` 与 `key-10`)与用户键序不一致。SQL 路径安全(FE 的主键编码保证用户键两两不互为前缀),裸 KV 范围扫描不保证 —— 详见设计方案 §7.1「已知约束」,P4 必须正面回答。

**④ 原子性与序号**:原子性不在 `mvcc.go`,在 `wal.go` —— 一次事务的所有写 + 元数据 + 计数器落在**同一条批记录**里,所以重放时"要么整表完整,要么完全不存在"(SC-208 验的就是这条)。序号不回退靠 `manifest.go` 的 `last_commit_ts` 与 WAL 里的值**取较大者**(INV-5,SC-206)。

## 三、FE 侧:三种读视图(这期最容易讲错的地方)

`txn/ReadViews.java` 把"读数据"分成了三种情形,记住这张表就记住了 P3 的语义:

| 工厂方法 | 用在什么时候 | 语义 |
|---|---|---|
| `ReadViews.latest(kv)` | **不在事务里**的普通语句 | 读最新已提交 |
| `ReadViews.ofTransaction(kv, txn)` | **事务里**读数据 | 按 `txn.snapshot()` 读 —— 快照一旦取定就不变(SC-207 验的"快照稳定") |
| `ReadViews.layered(base, overlay)` | 事务里读**自己改过**的数据 | **读己之写**:自己的 `WriteSet` 盖在快照上 |

`Transaction` 本身极薄(41 行):`txnId` + `snapshot` + `writes`,没有锁、没有等待队列 —— 因为 P3 的并发控制是**提交时检测写写冲突**(乐观),不在读路径上加锁。冲突时抛 `ConflictException`,由 Executor 翻译成"表名 + 主键"的可读错误(SC-202 验的"不带 Java 堆栈")。

## 四、一次事务从 SQL 到落盘(逐跳)

```
BEGIN       FE --BeginTxn--> BE                     返回当前水位当快照
            FE 建 Transaction(txnId, snapshot)
事务内 INSERT  写进 WriteSet;读走 layered(快照 + 自己的写集)
COMMIT      FE 把整批写 --CommitTxn--> BE
              BE: 冲突检测(写集里每个键的最新版本 vs 快照)
                  → 通过:一次 WAL 批记录 + fsync(日志先于数据)
                  → 冲突:回明确错误,什么都不写
            BE 把 commit_ts 编进 key 的版本段,推进 last_commit_ts / MANIFEST
            返回 commit_ts 给 FE,事务结束
崩溃重启    WAL 重放;last_commit_ts 取 MANIFEST 与 WAL 的较大者 → 序号不回退
```

## 五、四个崩溃注入点分别证明什么

`config/be.conf` 的 `test_crash_point` 让 BE 在指定位点**立即退出**,`p3-test.sh` 逐个验证:

| 注入点 | 位置 | 期望 | 实测 |
|---|---|---|---|
| `before_wal` | 还没写日志 | 事务**不可见** | ✅ 不可见;后续新事务 `commit_ts=19` 正常 |
| `after_fsync` | 日志已 fsync,memtable 未写 | **可见**(已完整落盘 = 已提交) | ✅ 可见且值一致;新事务 `commit_ts=20` |
| `after_memtable` | memtable 已写,尚未返回 OK | **可见** | ✅ 可见且值一致 |
| (WAL 尾部截断) | 手工截断最后一条批记录 | 该事务**整体丢弃**,之前数据完好 | ✅ 全过 |

> 顺带说明:`after_fsync` 那一格原来在规约里被写成"不可见",与 FR-313/315 自相矛盾 —— 这就是 I6,已按 FR 修正。

## 八、这一期最该记住的三件事

1. **版本段在 key 尾部、且倒序** —— 所以"读最新 = 读第一条"、"按快照读 = 第一条 ≤ 快照"。这一条解释了 P3 为什么没有在读路径上加锁。
2. **原子性来自"一条 WAL 批记录"**,不是逐条写 —— 所以"要么整表完整,要么完全不存在"是**结构上**成立的,而不是靠代码里的小心。
3. **序号不回退**:`last_commit_ts` 取 MANIFEST 与 WAL 的较大者。这条反直觉(数据都进 segment、WAL 都回收了还得知道"曾经到过哪"),但它是 INV-5 的全部内容。
