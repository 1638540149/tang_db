# P1 读代码地图

> 这份文档是给你读代码用的。P1 的代码不是你写的,但**你得能讲明白它怎么跑**——否则这个项目就只剩"我有一个能跑的库",而不是"我懂它是怎么跑起来的"。
>
> 建议配合真实文件打开对照读,不要只读这份文档。

## 1. 启动 BE 时到底发生了什么

从 `./be.exe --config=config/be.conf` 到打印「BE 已就绪」,一条链走下来:

```
cmd/be/main.go:44  run()
  │
  ├─ loadConfig("--config")               main.go:128    读 config/be.conf(不存在则退回内置默认值)
  ├─ flag.Visit → 命令行参数覆盖配置       main.go:55     优先级:命令行 > 配置文件 > 内置默认值
  │
  ├─ config.ParseSize("64MB")             config/config.go:110   把 "64MB" 变成 67108864
  │
  ├─ store.Open(dataDir, memtableSize)    engine.go:54   ← 恢复全在这里
  │    │
  │    ├─ manifest.Open(dir)              manifest.go:41
  │    │    └─ Registry.Load()            manifest.go:60  读 CURRENT → 读 MANIFEST 文件
  │    │                                               得到:有效的 segment 列表 + 当前 WAL 编号
  │    │
  │    ├─ 逐个 segment.Open(path)         segment.go:258  读文件尾部 Footer,再载入 Index 与 ZoneMap
  │    │                                               ★ 只读尾部元信息,不把数据全读进内存
  │    │
  │    ├─ wal.Open(dir, maxNumber+1)      wal.go:93      开一个新的 WAL 文件准备接着写
  │    │
  │    ├─ 旧 WAL 逐个 Replay             wal.go:195
  │    │    └─ replayReader(reader, fn)   wal.go:206   ← ★ 崩溃恢复的核心
  │    │         逐条读:读头 → 校验 CRC32C → 解码 → 回调灌进 memtable
  │    │         遇到「读不满一条」或「CRC 不对」→ 就地停止,丢弃后面全部内容
  │    │
  │    └─ go flushWorker()               engine.go:292  后台刷盘线程启动
  │
  ├─ server.NewTangDbServer(engine)      server.go:23
  └─ grpc 监听配置里的 port(默认 :9100)
```

**要记住的一句话**:启动 = 读配置(config/be.conf + 命令行覆盖)→ 读清单(MANIFEST)→ 装载已落盘的文件(segment)→ 把日志里还没落盘的补回来(WAL 重放)。

## 2. 一次 `put` 走了哪几跳

这是整个 P1 最该看懂的一条路径,因为它决定了"数据为什么杀不掉"。

```
Clava CLI 敲下: put name wangyu
  │
  └─ Cli.java → TangDbClient.put() → gRPC
        │
        └─ server.go:36  TangDbServer.Put()
              │
              └─ engine.go:178  Engine.Put(key, value)
                   │
                   ├─ ① 校验:key 非空、value ≤ 1MB
                   │
                   ├─ ② walFile.Append(key, value)      wal.go:114
                   │      ├─ encodeRecord               wal.go:172
                   │      │    组装:CRC32C(4) + Type(1) + PayloadLen(4) + Payload
                   │      ├─ bufWriter.Write            wal.go:69   先攒在内存缓冲里
                   │      └─ Sync()                     wal.go:159
                   │            └─ bw.Flush()  ← 先把缓冲刷进文件
                   │            └─ f.Sync()    ← ★ 真正的 fsync,数据落到盘片
                   │
                   ├─ ③ e.mem.Put(key, value)           memtable.go:40  跳表插入(纯内存)
                   │
                   ├─ ④ 检查 ApproximateSize() ≥ threshold ?           memtable.go:103
                   │      └─ 是 → rotateMemtableLocked()  engine.go:264  冻结当前表
                   │
                   └─ return nil    ← ★ 到这里才返回 OK
```

**关键点**:第 ② 步的 `f.Sync()` 发生在返回 OK **之前**。所以只要客户端收到 OK,这条数据就一定在磁盘上了。这就是"`taskkill /F` 杀不掉数据"的全部秘密 —— 不是魔法,是顺序。

> 代码里的注释也写明了这一点(`engine.go:194` "① + ②:先写 WAL 并 fsync")。但注释不算证据 —— 我核验时是直接读的代码,并另外用 Python 独立解析 WAL 文件重算了 CRC 来验证。

## 3. 一次 `get` 走了哪几跳

```
server.go:61  TangDbServer.Get()
  └─ engine.go:217  Engine.Get(key)
       │
       ├─ ① mem.Get(key)              memtable.go:85   当前可写的内存表
       │      命中 → 立即返回 ★
       │
       ├─ ② 遍历 e.imm(不可变表,从后往前)  engine.go:229
       │      命中 → 立即返回 ★
       │
       ├─ ③ 遍历 e.segments(新 → 旧)      engine.go:234
       │      └─ seg.Get(key)             segment.go:306
       │            ├─ 用 Index Block 定位到候选 chunk     searchChunk segment.go:323
       │            ├─ 用 ZoneMap 判断这个 chunk 有没有可能含 key
       │            └─ 在 chunk 内二分查找
       │      命中 → 立即返回 ★
       │
       └─ 全都没命中 → return nil, false → server 转成 NOT_FOUND
```

**为什么顺序必须是"从新到旧"**:同一个 key 可能既在老 segment 里有旧值、又在 memtable 里有新值。如果顺序反了,或者命中后还继续往下找,就会读到过期数据。**任一环节命中就必须立刻停。**

## 4. memtable 写满时发生了什么

这是"前台不停、后台干活"的经典结构:

```
前端写入途中发现 ApproximateSize ≥ 阈值
  │
  └─ rotateMemtableLocked()            engine.go:264
       ├─ 当前 memtable 改标记为「不可变」,塞进 e.imm
       ├─ 新建一个空 memtable 继续接受写入   ← ★ 前台立刻可以继续写,不等刷盘
       └─ 唤醒 flushWorker
            │
            └─ flushWorker()           engine.go:292   后台 goroutine
                 └─ flushAll()          engine.go:305
                      └─ flushOne(table, segNum)   engine.go:328
                           ├─ segment.NewBuilder(path)   segment.go:62
                           ├─ 逐条 Add(key, value)       segment.go:67    攒进内存的行缓冲
                           ├─ Finish()                   segment.go:75
                           │     按列切分 → 各列独立 chunk(4096 行/块)
                           │     → 写 ZoneMap(每列 min/max)
                           │     → 写 Index Block(每 chunk 首 key + 偏移)
                           │     → 最后写 Footer(含 magic、偏移、行数、校验和)
                           ├─ manifest Registry.Save()   manifest.go:86   ← ★ 原子更新:
                           │                                                  写临时文件 → rename
                           │                                                  → fsync 文件 + fsync 目录
                           ├─ 从 e.imm 移除这张表
                           └─ gcWAL()                    engine.go:371   ← ★ 这时才可以回收 WAL
```

**两个顺序陷阱**(P1 里最容易写错、也最值得你记住的地方):

1. **segment 先落盘 + MANIFEST 先更新,WAL 才能删**。反过来的话,一旦在中间崩了,数据既不在 WAL 也不在清单里 → 永久丢失。
2. **MEMTABLE 的冻结要立刻换新表**,不能等刷完再换。否则刷盘那几百毫秒里,前台写入全被堵住。

## 5. 建议的阅读顺序

按这个顺序读,由浅入深:

| 顺序 | 读什么 | 为什么 |
|---|---|---|
| 1 | `proto/tangdb.proto` | 十分钟看完接口,先知道边界在哪 |
| 2 | `be/cmd/be/main.go` | 146 行,看进程骨架:先读配置,再装配引擎(config/be.conf 与命令行覆盖的关系在这里) |
| 3 | `be/internal/memtable/memtable.go` | **最好懂的一个**:跳表 + 迭代器,纯内存结构 |
| 4 | `be/internal/store/engine.go` 的 `Put` / `Get` / `Open` | 引擎主干,三个函数 |

## 6. 几个值得注意的实现细节

这些都是 LSM 系统里"踩过才知道"的地方,值得留意作者怎么处理的:

1. **Footer 放在文件末尾**(`segment.go:215 writeFooter`)
   打开 segment 时只需读文件尾部固定长度,就能拿到全部元信息的位置 —— 不用从头扫。这是列式文件的标准做法。

2. **bufWriter 缓冲,但 fsync 前必定 Flush**(`wal.go:59-90`、`wal.go:159`)
   攒批减少系统调用,但不能因此丢数据 —— 所以 `Sync()` 里先 `Flush()` 再 `f.Sync()`。

3. **WAL 重放遇坏记录就停,不报错**(`wal.go:206 replayReader`)
   崩溃时最后一条写必然是不完整的。这时**不能报错退出**,要在那里截断、丢弃后半段,让服务正常起来。这是"恢复"和"校验"的区别。

4. **MANIFEST 更新是 写临时文件 → rename → fsync**(`manifest.go:86`、`manifest.go:168`、`manifest.go:177`)
   rename 在同一文件系统内是原子的,所以任何时刻磁盘上要么是旧清单、要么是新清单,不会出现半截。注意还要 `fsync` **目录**才能保证 rename 本身持久化 —— 这一步很容易漏。

5. **WAL 回收有严格前置条件**(`engine.go:371 gcWAL`)
   只有 segment 已经落盘、并且 MANIFEST 已经记录了它,才能删掉对应的 WAL 段。顺序反了就是丢数据。

6. **Get 的短路返回**(`engine.go:226-242`)
   三处命中点都是立即 `return`,没有"继续找找看"。这是正确性问题,不是性能问题。

7. **配置只在一处解析**(`be/internal/config/config.go`、`fe/src/.../FeConfig.java`)
   两个进程读的都是 `config/` 下那两份 `key = value` 文本,语法一模一样,但各自用本语言的标准库手写解析 —— BE 侧一个第三方库都没引(依赖红线)。未知配置项、格式错误、取值非法一律**报错退出**,不静默忽略:配置写错了,启动就该失败。命令行参数在配置之后覆盖同名项。

## 7. P1 **没有**做的事(以及为什么)

| 没做 | 因为 |
|---|---|
| **Compaction(分层合并)** | P1 只验证正确性。segment 文件只增不合,长期跑会让读放大越来越大 —— 这是**已知的、可接受的**技术债,后续期次解决 |
| **版本号 / MVCC** | 属于 P3。P1 的 key 是裸字节,同一 key 覆盖即丢弃旧值 |
| **表 / SQL / 索引** | 属于 P2 及以后 |
| **列块压缩编码** | 列的**结构**已经按列组织好了,但编码还是原始的。P5 换编码方式时不需要改文件布局 —— 这是当初把"结构"和"编码"分开的原因 |
| **FE 元数据持久化** | 设计已定(存进 BE 自身系统表),落 P2 |
| **BE 注册与心跳** | 设计已定(BE 主动 push),落 P2 |

## 8. 上手改代码前要记住的三条

1. **Put 的 ①→②→③ 顺序不能动**。任何"优化"只要把 memtable 写到 fsync 前面,就把整个项目的可靠性根基拆了。
2. **segment 文件写完不能改**。要改就写新文件 + 原子换 MANIFEST。
3. **FE 不许碰数据目录**。哪怕只是想"看一眼对不对",也必须走 gRPC。
