# 读代码地图 · P6.1(增量:执行层性能这一跳怎么走)

> 本期不改语义,只改"每条语句要摸几次内存/几次磁盘/几次系统调用"。读代码时请始终带着一个问题:**这条路径上,同样的结果能不能用更少的次数算出来。**
> 本文只讲本期新增的这一跳;P1~P6 的地图各自成篇,不重复。

## 一句话

一次写 = **排序去重 → 单次区间冲突检测 → 追加 WAL(不 fsync)→ 等覆盖自己的那次分组 fsync → 应用 memtable → 回 OK**;
一次读 = **FE 决定列掩码与谓词字节码 → 按 key 范围切片并发下发 → BE 按偏移切片、按字节比较过滤、按列式块回传 → FE 只解码用得到的列**。

## 主链路

### A. 写路径(一条 INSERT / 一批导入)

```
fed / CLI ──gRPC CommitTxn──► server.CommitTxn (server.go:356)
                                   │
                                   ▼
                        store.Engine.Commit (engine.go:434)
                        ├─ commitMu 内
                        │   ├─ prepareWrites           (conflict.go:13)   排序 + 同 key 留最后一次写
                        │   ├─ detectConflicts         (conflict.go:54)   一个 scanner 扫写集首尾区间
                        │   ├─ 查 pending 表            (engine.go:491)    已追加未应用的写也算冲突
                        │   ├─ 取 commit_ts
                        │   └─ WAL 追加(不 fsync)      (wal.go appendRecordBuffered)
                        └─ commitMu 外
                            └─ waitDurableAndApply     (group_commit.go:28)
                                ├─ 组 leader 做一次 w.Sync()   ← 多个事务共用
                                ├─ takePending / applyBatch(group_commit.go:134 / 181)
                                └─ 推进 durableSeq → 唤醒同组等待者 → 返回 OK
```

要点:
- **返回 OK 仍然等价于"覆盖本事务的那次 fsync 已完成"**(FR-698),group commit 只是把 N 次 fsync 并成 1 次,不改红线。
- 冲突检测的扫描次数与写集大小无关(一次 `newScanner`),这是 SC-400 从"每 key 一次扫描"降到 3ms 以内的原因。
- `failedSeq`(group_commit.go:33)是补上的口子:某批 fsync 失败后,后续水位即使追平也**不许**把这一批报成成功。
- 惰性游标 memtable.go:145(`Iterator`)/154(`IteratorAt`)/177(`IteratorSnapshot`):创建时只记写计数水位,`Next/Seek` 越过水位返回 `ErrUnsafe`,由上层重建 —— 这里**没有**静态快照,长生命周期调用方必须显式用 `IteratorSnapshot()`。

### B. BE 读路径(一次 Scan)

```
FE: QueryEngine.scanShards (QueryEngine.java:916)
 ├─ shardBoundaries(…)      (QueryEngine.java:982)  按字节空间等分成 N 片,首片从原始 start 起
 ├─ 固定一个快照 kv.snapshotPin()(KvStore.java:46)  所有片共用,并发写不会让不同片看到不同版本
 └─ 每片 scanProjected(…)   (ReadViews.java:42 → ProjectingStore)
        │
        ▼
BE: server.Scan (server.go:166)
 ├─ buildScanPlan (server.go:130)  解析 column_mask / column_slots / row_frame / predicate
 ├─ sc := engine.NewMVCCScanner(…)  与 P6 同一条 MVCC 扫描,只是"取出来之后"做得更少
 ├─ 谓词: exec.ParsePredicate(predicate.go:56) → Predicate.Eval(predicate.go:168)
 │        └─ 值转比较态: exec.CompareBytes(predicate.go:379)(BE 只做字节比较,不认类型)
 ├─ 投影: exec.NewRowLayout(projection.go:110) → RowLayout.ProjectRow(projection.go:191)
 │        └─ 产出 [nullmap][len][bytes]×n 帧,只含被选中的列
 └─ 回传:encodeColumnarBlock(server.go:318) → RowBatch.columnar_block
```

要点:
- **BE 依然不知道表名/列名/类型**:slot 表(`column_slots`)由 FE 按表定义生成(`ProjectedCodec.encodeSlots`,ProjectedCodec.java:81),BE 只按偏移切片。
- 谓词是**栈式字节码**(`predicate.go:14` 起的指令集):操作码 + 列槽号 + 保序编码后的字面量。JSON 列不下推(边界 #114),留在 FE 侧当残余谓词。
- 乱序风险的两个补丁值得单独看:字符串按**有符号字节序**比较(`SLOT_VARLEN_SIGNED`),FE 与 BE 两侧一起翻最高位,否则非 ASCII 谓词会漏行。
- 剪枝只做到"key 范围跳前缀 chunk"(`segment/iter.go:114` → `segment.go:750` 计数),**没有**按列值的 zone map —— 磁盘格式里没有值列统计,加它等于改格式(K154 禁止)。

### C. FE 执行侧

- 并行度/下推开关注入:`Executor.withExecution`(Executor.java:145)→ `SqlEngine`(SqlEngine.java:80)→ `QueryEngine` 的 `options`。
- 只有"无 LIMIT 下推、最新视图、真能投影的客户端、并行度 > 1"才并发(QueryEngine.java:916 的 `canParallel`);任一片失败 = 整条查询失败(边界 #121)。
- `LIMIT` 提前终止靠"整条谓词可下推"判定(`fullyPushable`,QueryEngine.java:901):BE 先过滤再截断,才与"FE 过滤后截断"等价。
- 解码复用:`ProjectedCodec.decode`(ProjectedCodec.java:116)把帧还原成与表定义等宽的 `Object[]`,未选中列留 null。
- `EXPLAIN` 新增"并行/批/下推"一行(Executor.java:1062 / QueryEngine.java:2829),P4/P5/P6 既有行不动(SC-414)。

## 与本期的边界(读代码时最容易怀疑的地方)

1. **算子的并行阈值已有、但扫描分片还没有**:`query/Parallel.java:21` `MIN_ROWS = 2048` 是**算子层**(排序/聚合/JOIN)的开关门槛;`QueryEngine.scanShards`(:916)按 key 范围切片的**扫描层没有任何行数门槛**,所以 `LIMIT 10` / `DISTINCT` / 小投影这类查询照样被切成 8 片、付线程池 + 8 次 RPC 的固定开销(实测 p8 比 p1 慢 1.5~2 倍)。要治的是扫描层,不是把 `MIN_ROWS` 调大。
2. **结果集仍是先物化再写 socket** —— FR-715 的流式没做,`LIMIT` 提前终止是"下推到扫描"实现的,不是协议层取消。
3. **`ProjectedCodec.decode`(:116)每行 `new Object[]`** —— FR-716 的解码复用没做,装箱开销还在;`SHOW SESSIONS`(`SqlEngine.java:457`)也没有并行度/批/下推三列(FR-719 只做了 EXPLAIN 那一半)。
4. **列式块与逐 KV 两条路径并存** —— `columnar_result=false` 或没有投影参数时回退 `Rows []*pb.Kv`(FR-707/710),混用视为内部错误(边界 #118)。
5. **批大小自适应落在 BE**:`server.go:22-26` 的 1,024/4,096/8,192 + 2MB 字节预算,`:289` 切批;FE 只是把 `scan_batch_rows` 原样下发(FR-708 已实现,FR-717 的 FE 侧自适应没做)。
6. **`SHOW SEGMENTS` 的剪枝两列是进程累计值**,不是"本次扫描"的增量。

1. `be/internal/store/conflict.go`(90 行,最短,先看清"做了什么、为什么一次就够")
