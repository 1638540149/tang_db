# 读代码地图 · P6(增量:优化器这一跳怎么走)

> 只讲 P6 新增/改写的那一跳。P1~P5 的地图见同目录各期文件;这里给"从 SQL 文本到计划选择"的完整路径,以及每一跳对应哪个文件、哪个方法。

## 一句话

P6 把"怎么查"从**固定规则**换成**有据可依**:先有统计(`stats` 包 + 两张系统表),再有估算(`Estimator` + `CostModel`),最后由 `QueryEngine` 按估算选访问路径、连接顺序、连接算法、聚合与排序实现;不变式是**只改"怎么跑",不改结果**。

## 主链路(自上而下)

```
SQL 文本
  → Parser(AST)
  → SqlEngine 分发(EXPLAIN / ANALYZE / SHOW STATS / DML / 查询)
  → 查询走 QueryEngine:
       ① 统计读取     stats/TableStats + ColumnStats(来自 sys_table_stats / sys_column_stats)
       ② 基数估算     planner/Estimator(选择率公式表 → 行数)
       ③ 代价模型     planner/CostModel(9 个相对代价常量)
       ④ 路径选择     planner/Planner.chooseIndexPath(索引点/范围/全表扫 的代价比较)
       ⑤ 连接决策     QueryEngine.planJoins(顺序 + 算法 + build 侧)
       ⑥ 表达式改写   query/ExprOptimizer(常量折叠、谓词下推标记、列裁剪)
       ⑦ 执行         向量化算子(batch 1024,单线程)+ Sorter / Aggregates
  → 结果集
```

## 与本期的边界(读代码时最容易怀疑的地方)

1. **`proto/` 与 `be/` 零改动**:统计走已有 `Scan` / `CommitTxn`,`git diff` 里这两个目录为空。所以"BE 不懂表列"没有任何被打破的风险。
2. **系统表 ID 7 / 8**:`sys_table_stats` / `sys_column_stats` 的 key = `db_name + table_id` 与 `table_id + ordinal`,与用户表 key 空间按表 ID 段天然隔开。
3. **虚拟表 17 → 18**:新增 `information_schema.PARAMETERS`(恒空表),`P4` 里"17 张"的断言随之改成 18 —— 这是 `scripts/tests/p4-test.sh` 唯一被改的地方。
4. **`optimizer_enabled`**:唯一的总闸。关掉后路径选择回到 P5 的固定规则,`SC-375` 用它做 12 条 SQL 的结果对拍。

## 读这一期建议的顺序

1. `stats/` 四件套(HLL → Histogram → StatsCollector → StatsStore):把"统计长什么样"看明白;
2. `planner/Estimator` → `planner/CostModel` → `Planner.chooseIndexPath`:把"怎么算代价"看明白;
3. `QueryEngine.planJoins` + `explain`:把"代价怎么变成计划、计划怎么被解释"看明白;
4. 语法四件(Union / Exists / Distributed / DerivedTable)与 `SqlEngine` 的门禁删除:看"补了哪些语法面";
5. 最后回头看 `scripts/tests/p6-test.sh` 的 SC 段,逐条对回代码。
