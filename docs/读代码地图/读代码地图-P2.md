# P2 读代码地图

> 这份文档是给你读代码用的。P2 的代码不是你写的,但**你得能讲明白一条 SQL 在库里走过哪些地方** —— 否则这个项目就只剩"我有一个能跑 SQL 的库",而不是"我懂它是怎么跑起来的"。
>
> 建议配合真实文件打开对照读。所有行号按 2026-10-22 的 P2 代码状态标注。

## 1. 一条 SQL 从敲下到出结果的完整一跳

这条链是 P2 的主干,**看懂它就懂了 80%**:

```
你在 CLI 敲: CREATE TABLE users (id BIGINT PRIMARY KEY, name VARCHAR(32));
  │
  ├─ Cli.run                                    Cli.java:184 附近
  │    ├─ SqlBuffer.append(line)                SqlBuffer.java:19   先把行攒起来
  │    └─ 遇到 ';' → 取出一整句                    SqlBuffer.java:66
  │
  ├─ Parser.parse(sql)                          Parser.java:35      词法 → 语法 → AST
  │    ├─ Lexer.tokenize()                      Lexer.java:23
  │    └─ parseStatement() 分派                 Parser.java:45
  │         CREATE→65  DROP→117  TRUNCATE→123
  │         SHOW→129  DESC→137  INSERT→142  UPDATE/DELETE/SELECT …
  │
  ├─ Executor.execute(ast)                      Executor.java:38    ← 真正干活的地方
  │    ├─ 查表:catalog.require(表名)             Catalog.java:80
  │    ├─ DDL:createTable / dropTable / truncateTable
  │    │        Catalog.java:110 / 130 / 153
  │    ├─ INSERT/UPDATE/DELETE:
  │    │        KeyCodec 算出主键 key → RowCodec 编码值 → kv.put
  │    │        Executor.java:148/153(插入前查重)、183(更新)、194(墓碑)
  │    └─ SELECT:
  │         ├─ Planner.access(table, where)     Planner.java:60 起
  │         │     主键等值 → Plan.point          Planner.java:148(单点)/155(IN 多点)
  │         │     主键范围 → Plan.range          Planner.java:164
  │         │     其它条件 → 全表 Plan.range      Planner.java:166
  │         ├─ 点查:kv.get(key)                  Executor.java:244
  │         └─ 范围:kv.scan(start, end, limit)   Executor.java:259
  │               └─ FE 侧过滤/投影(谓词下推留给 P5)
  │
  ├─ KvStore 接口实现 = TangDbClient            TangDbClient.java:224/233/242
  │    ├─ getRaw(byte[])                        TangDbClient.java:146
  │    ├─ putRaw(byte[], byte[])                TangDbClient.java:168
  │    └─ scanRaw(start, end, limit)            TangDbClient.java:192   ← 流式收 RowBatch
  │
  └─ BE 侧(TangDbServer)                        server.go:39/64/97
       ├─ Put → engine.Put → WAL+fsync → memtable(P1 的老路径,没动)
       ├─ Get → engine.Get → memtable → segment
       └─ Scan → engine.NewScanner(...)          engine.go:440 → 见 §4
```

**一句话记住**:SQL 的语义全在 FE(表名、列名、类型、条件),BE 只收到 **key 范围**和**字节值** —— 这条线 P1 立的,P2 没有破。

## 2. key 与 value 怎么编码(表、索引、版本都靠它区分)

| 事 | 在哪 | 要点 |
|---|---|---|
| key 布局 | `KeyCodec.java` | `[表 ID 4B][索引 ID 4B][主键保序编码][主键值(主键索引里为空)][版本 8B]`;**版本本期固定写 0**(K15),P3 启用 MVCC 时不用改布局 |
| 主键保序编码 | `KeyCodec.java` | INT/BIGINT/BIG/DATE 走大端 + 符号位处理,VARCHAR 走原始字节 + `0x00` 终止 —— 保证"字节序 = 数值/字典序" |
| 表范围 | `KeyCodec.tableRangeStart(tableId)` | 全表扫描就是从"表 ID 起点"扫到"表 ID 终点" |
| 行值 | `RowCodec.java` | `[格式版本 1B][表 ID 4B][列数 2B][NULL 位图][列值…]`;NULL 列不占列值空间 |
| 墓碑 | `RowCodec.encodeTombstone(tableId)` | DELETE 不是擦除,而是写一个"墓碑值";查询解出来标记 tombstone 就跳过 |
| 值转换/比较 | `Values.java` | 常量与列的隐式提升(INT→BIGINT→DOUBLE)、DATE 解析、`VARCHAR` 按字节数校验 |

> 这就是"**FE 编码、BE 存字节**"的落地方式:BE 不知道什么是主键,它只知道 key 的字节序。

## 3. 元数据怎么从 BE 的系统表长出来

这是 D11 的落地:**不用任何外部数据库,元数据存在库里自己的表里**。

```
Catalog.open(kvStore)                        Catalog.java:45
  ├─ bootstrapSystemTables()                 Catalog.java:180   幂等建系统表(空库也能起来)
  │    表 ID 由 SystemTables 固定:1=表定义 2=列定义 4=计数器,用户表 ID ≥ 16
  │
  ├─ loadAll()                               Catalog.java:206
  │    ├─ readTableRows()                    Catalog.java:287   扫 sys_tables 范围
  │    ├─ readColumnRows()                   Catalog.java:306   扫 sys_columns 范围
  │    └─ loadCounter()                      Catalog.java:341   读 next_table_id
  │    任何一条不完整(缺列、没有主键、计数器非法)→ 抛 CatalogException,FE 启动失败(FR-117)
  │
  └─ 内存里两份索引 + 一把读写锁               Catalog.java:34/36/37
       byId(tableId→表)  activeByName(表名→表)  ReentrantReadWriteLock

DDL 写回:
  createTable → allocateTableId(374) 取号 → 写系统表 + 内存      Catalog.java:110
  dropTable   → 标 dropped(表 ID 不复用)                        Catalog.java:130
  truncateTable→ 换一个新表 ID(等价于新空表,旧数据不再可见)      Catalog.java:153
```

**为什么 FE 启动必须先连上 BE**:权威副本在 BE,FE 内存里那份只是缓存。所以"FE 写完系统表、还没更新内存就崩了"这种担心不成立 —— 重启后从系统表重建即可(这也是 §4.4 那条边界澄清的实现依据)。

## 4. BE 侧:范围扫描怎么做到"不重、不漏、取最新"

```
server.Scan(req, stream)                     server.go:97      服务端流式
  └─ engine.NewScanner(start, end, limit)    engine.go:440
       ├─ 组游标(Cursor 数组):
       │    ├─ memtable(最新,在内存)            exec.NewMemCursor     exec.go:160
       │    ├─ 不可变 memtable(若存在)
       │    └─ 每个 segment 一个有序迭代器        segment/iter.go:24
       │          按 chunk 顺读,不满一条就停下   iter.go:102/115
       └─ exec.NewScanner(cursors, …)         exec.go:55        ★ 多路归并
            └─ Next()                         exec.go:65
                 同一 key 只出一次;多个游标都有同一个 key 时**取最新的那层**(memtable 优先)
                 出错的游标记录错误 → 通过 RowBatch 的状态或 gRPC 错误明确结束(不静默截断)
```

顺带把**点查**那条也记住(这是 P1 的路径,P2 没改):

```
engine.Get(key) → memtable → 不可变表 → segment 新到旧,命中即返回   engine.go:239
   └─ segment.Reader.Get(key)                                    segment.go:306
        ZoneMap 逐 chunk 判断 [keyMin,keyMax] → 命中就解 key 列 + value 列(4096 行/块)→
        块内线性比较
```

现状与待优化(设计文档 §6.3.1 记的四级阶梯):目前是 ZoneMap 过滤 + 块内线性;**Index Block 二分、块内偏移数组、块级布隆**都还没做,登记在 P5。

## 5. 心跳这条链路怎么闭环(P2 的另一半)

```
BE 侧(客户端角色)                              FE 侧(服务端角色)
────────────────────────────────────────      ──────────────────────────────────────
beid.LoadOrCreate(dataDir)  beid.go            FeGrpcServer.start(port, registry)  FeGrpcServer.java
  └─ 首次生成 UUID → 写 <data-dir>/be.id          └─ FrontendService                  FrontendService.java:23/43
     重启后身份不变(K25)                              ├─ registerBe → registry.register
                                                    └─ heartbeat → registry.heartbeat
Reporter.Start(ctx)        heartbeat.go:56
  └─ loop()                heartbeat.go:94     BackendRegistry                    BackendRegistry.java
       ├─ register()       heartbeat.go:144       ├─ available(now, cycles)        :87
       │    失败 → 指数退避重试(上限 10s)          │   超过 interval×cycles 判不可用
       └─ 每 3 秒 heartbeat() heartbeat.go:164     └─ statusText → "可用"/"不可用"   :92
            载荷 = BuildHeartbeat()  heartbeat.go:69     ↑
            memtable 字节 / 不可变表数 / segment 数 / WAL 字节 /   SHOW BACKENDS 就是读它
            put·get·scan 计数 / 错误数 / 最后 fsync / 磁盘
```

配置入口:`config/be.conf` 的 `fe_host` / `fe_port` / `heartbeat_interval_seconds`;`config/fe.conf` 的 `heartbeat_listen_port` / `be_offline_cycles`。

**已知缺口(G2,记在 SPEC-P2 §11)**:BE 注册成功后若 FE 侧心跳服务消失再回来(比如 FE/CLI 重启),BE **不会重新注册** → `SHOW BACKENDS` 会一直空;只有重启 BE 才恢复。修法见规约待补充区。

## 7. 几个值得注意的实现细节

1. **Planner 只有三条路**(`Planner.java:148/155/164/166`):主键等值走点查、主键范围走 Scan、其它条件全表 Scan + FE 侧过滤。谓词下推与索引选择是 P5/P6 的事 —— 现在这样是**故意**的,不是漏了。
2. **INSERT 前先查一次主键**(`Executor.java:148`):这是 P2 的冲突检测,语义是"查一次再写",**并发下不保证唯一性**(§2.3 写明的边界)。P3 有了写写冲突检测才真正确。
3. **TRUNCATE 是换表 ID**(`Catalog.java:153`):O(1)、不依赖事务;代价是旧数据留在盘上不回收(等后续 compaction)。
4. **墓碑只要被解出来就跳过**(`RowCodec` + `Executor.java:249`):删除是写,不是擦,这是 LSM 的既定代价。
5. **BE 的 Scan 会记录扫描错误**(`engine.go:463 RecordScanError`):错误计数进心跳,便于从 FE 看到"BE 读得不顺"。
6. **FE 的心跳服务与 CLI 在同一个进程**(`TangDbClient` 启动 `FeGrpcServer`):所以"一个 FE 一个端口",端口被占 FE 直接起不来(G3)。
7. **元数据不完整就拒绝启动**(`CatalogException`):这是 FR-117 的实现,避免"静默当成空表"这种最坏情况。

## 8. P2 **没有**做的事(以及为什么)

| 没做 | 因为 |
|---|---|
| 事务 / MVCC / `BEGIN`·`COMMIT` | P3;本期 key 里的版本号字段固定写 0 占位 |
| 并发写的唯一性保证 | P3;本期是"查一次再写" |
| 二级索引 / 唯一索引 | P4;本期只有主键(索引 ID 固定 0) |
| JOIN / GROUP BY / 聚合 / 子查询 / ORDER BY | P5;本期 SELECT 只有投影 + WHERE + LIMIT |
| 谓词下推 / 列裁剪 | P5/P6;过滤全在 FE 侧 |
| 表达式与函数(含 `ai_embed`) | P7 |
| compaction 与物理回收 | 后续期次;segment 只增不合(P1 起的技术债) |
| `ALTER TABLE` / 多库 / 权限 | 不做或不在此期 |
| MySQL 协议 / `EXPLAIN` / Web 控制台 | P8 |

## 9. 上手改代码前要记住的四条

1. **FE 只碰 gRPC**:想"顺手读一下 BE 的数据目录"就是违规;要看数据走 `get`/`scan`。
2. **BE 不许出现表名/列名/SQL**:新增能力也要用"key 范围 + 字节"来表达,`proto/` 里一个 SQL 词都不许有。
3. **元数据的权威副本在 BE**;改 DDL 相关代码时,内存缓存与系统表必须同时维护,且启动加载要能发现"半套"。
4. **写路径顺序不动**:WAL → fsync → memtable → 返回 OK(P2 一条没改,别在这条上做"优化")。
