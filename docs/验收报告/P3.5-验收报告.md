## 四、§9 的 18 条边界抽检(落点)

| # | 情形 | 落点 |

## 六、实现期间修掉的三个真 bug(只有真实客户端才暴露)

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | JDBC 连不上(握手阶段断) | 随机盐可能含 `0x00`,客户端按 NUL 结尾字符串解析 part-2 → 握手被截断 | 盐从无 `0x00` 的字母表取样 |
| 2 | JDBC 换一种报错:盐被破坏 | Connector/J 把 seed 当 String 存再转回字节,非 ASCII 字节往返损坏 | 盐限定为 **20 字节可打印 ASCII** |
| 3 | `语法错误: 第 1 行第 1 列 无法识别的字符 '/'` | 客户端连接先发 `/* 版本 */ SELECT ...` | 执行入口剥离前导行注释/块注释(`SqlEngine.stripLeadingComments`),Lexer 支持块注释 |

这三处**在 CLI 自测里都发现不了**(CLI 用自己的客户端实现),属于"必须用真客户端"的价值验证。

## 七、未达标 / 未验证项与口径(必须明说)

### 7.1 性能:单行 INSERT P99 **11.50ms > 10ms**(未达标)

```
[性能] 单行 INSERT 延迟(与 SPEC-P2 SC-112 的 < 10ms 比较)
  INSERT 延迟: n=1000 avg=6.35ms p50=7.59ms p99=11.50ms max=22.77ms
```

- 对照:P3 期(CLI 直连 BE)同口径为 `P99=7.71ms`,**本期慢了约 3.8ms**。
- 原因:一次 INSERT 多了"CLI → `fed` 的 MySQL 协议往返(分帧/编解码) + `fed` → BE 的 gRPC 往返"这一跳,加上常驻进程内的会话/锁开销;这是**架构性代价**,不是实现 bug。
- 建议:①口径改为"经协议链路 P99 < 15ms"并在 P8 与监控指标一起做优化(组提交 / 连接内批量确认);②若坚持 10ms,则需把 `fed` 与 BE 合并部署或做本地快路径 —— 不建议现在动。**需所有者拍板口径**。

### 7.2 未验证项

| 项 | 状态 | 原因 / 口径 |
|---|---|---|
| DataGrip / Navicat GUI | ⚠️ 仅人工可验 | 无 GUI 自动化;连接前提已逐条核对(见 SC-313)。导航/自动补全可能因"三视图只做最小列 + 无 performance_schema"受限,**执行 SQL 正常** |
| 真流式结果集 | ⚠️ 归 P8 | 协议层按行发包,但 `Result.Table` 仍在 FE 内存聚合全部行(承 P2/P3 的 SELECT 实现);`max_allowed_packet` 硬上限同属 P8 |
| 边界 16 版本不兼容分支 | ⚠️ 未做 | CLI 与 `fed` 同源发布,不存在不兼容组合;握手已带版本串,将来跨版本再补比对 |
| TLS / 权限 / 服务端预编译 | 未做(§2.2 明确不做) | TLS 需另立决策;权限归 P13;`COM_STMT_*` 返回 1295 |

### 7.3 关于 p3 断言数 63 → 62

不是断言被删。真实原因:SC-209 的性能断言在本期由 `[PASS]` 变成 `[NOTE]`(P99 从 7.71ms 涨到 11.50ms,不再满足 `< 10ms`),该条不再计入 PASS,总数自然少 1。脚本静态断言点反而比 P3 期多一处(`bad "nohb fed 启动失败,FR-367 未验"`)。

两处必须说明:
- **Windows 上 `stop` 实际走强制结束**。`taskkill` 不带 `/F` 送不到 SIGTERM,`taskkill(PID)` 对控制台程序无效,脚本在 5~6 秒后回退 `/F`。所以"优雅退出(FR-413)"在 Windows 上只有**前台 Ctrl+C**这一条路径能验;强杀不丢已提交数据(WAL 已 fsync),只丢未提交事务 —— 与 `crash-test.sh` 口径一致。
- **`fed` 中文乱码已修**:Java 17 的 `System.out/err` 用控制台默认编码(中文 Windows = GBK),只加 `-Dfile.encoding=UTF-8` 改不了 stdout。脚本现在额外带 `-Dsun.stdout.encoding=UTF-8 -Dsun.stderr.encoding=UTF-8`,git-bash(mintty,UTF-8)里中文正常。BE 是 Go 直接写 UTF-8,所以一直没有这个问题。
