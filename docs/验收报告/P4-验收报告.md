## 四、§9 三十条边界抽检

| 组 | 覆盖情形 | 落点 / 结论 |
|---|---|---|
| 索引 DDL 边界(1~6) | 列不存在、主键列、同列重复建、重名(1061)、非法名、非空表且有重复值 | `Catalog.createIndex:472` 与 `Executor` 的 DDL 分支;重复值报"重复值 + 前两个主键"且不留半成品 |
| 回填与状态(7~8,17) | 回填中断可续、回填期并发写、`BUILDING` 查询退全表扫 | `Executor.backfill:518` + `sys_indexes.build_cursor`;I16 拍板 A → 回填期写入也进索引 |
| 唯一与 NULL(9~12) | 多行 `NULL` 允许、改成 `NULL` 允许、同事务多次改只留最终版、同事务两行同值 | `IndexCodec.entryKey` 只对非 NULL 建项;写集按用户键去重 |
| 读路径(13~16) | 索引项指向已删行 → 跳过;行值已改 → 二次校验跳过;索引条件 + 残余过滤;`OR` 退化 | `Executor.forEachIndexMatch:1080`、二次校验 `:1115` |
| 生命周期(18~20) | `DROP` 后同名重建、`DROP TABLE` 后不可见、`TRUNCATE` 后老索引不可见 | `Catalog.dropIndex:538`、表状态联动 |
| `EXPLAIN`(21) | 解释 `INSERT`/DDL/事务语句 | 明确报"不支持解释该语句" |
| 编码(22) | 索引列 `VARCHAR` 内含 `0x00` | `IndexCodec` 的转义(K77),往返用例覆盖 |
| 限额(23) | 索引写入导致 `max_txn_write_bytes` 超限 | 整批失败、无副作用,错误信息说明"含索引写入" |
| 元数据(24) | 索引指向不存在的表/列 | 启动报错指名对象(K26 沿用) |
| 客户端(25~30) | `LIKE` 无匹配空集、`CREATE TABLE` 不存在 1146、`KILL` 无效 id、`information_schema` 上 JOIN 明确 1235、虚拟表 `ORDER BY`/`COUNT(*)` 已支持、空库树为空集 | `MetaCommands` + `SqlEngine` 兼容层 |

## 六、性能(同报条件)

机器:本机开发环境,Windows 11,数据目录 `tmp/p4-test/data`(SSD),BE 9900 / fed 9906,**热缓存**,每项 3 次取最优。

**索引路径 vs 全表扫(表 `perf`,2 万行,`WHERE k = <常量>`)**

| 路径 | 耗时 | 扫描行数 |
|---|---|---|
| 索引扫描 + 回表 | **409 ms** | **1**(日志:`索引扫描 表=perf 索引=idx_k 索引项=1 回表=1 命中=1`) |
| 全表扫 | 402 ms | 20000 |

> **诚实解读**:两者耗时几乎一样 —— 因为 400ms 里绝大部分是 **CLI/fed/协议的一次往返开销**(每条语句都要起一次会话级调用),真正干活的差别体现在**扫描行数 1 vs 20000**(相差 4 个数量级)。等 P8 的协议层优化与 P6 的 CBO 到位,这个时间差才会体现出来;**现在不要用"耗时一样"当结论说索引没用**。

**单行 INSERT 延迟(索引数 0 / 1 / 3,n=300)**

| 索引数 | avg | p50 | p99 | max |
|---|---|---|---|---|
| 0 | 9.64 ms | 8.63 ms | 38.27 ms | 97.62 ms |
| 1 | 8.97 ms | 9.06 ms | 14.42 ms | 15.96 ms |
| 3 | 14.10 ms | 13.86 ms | 19.07 ms | 26.02 ms |

> 3 个索引时 avg 从 ~9ms 涨到 **14.1ms**(每条索引多一次写入与同批体积),符合预期;写放大只记录不设门限(P5 起生效,K90)。

## 八、实机(Navicat)反馈的三类问题与处置

用 Navicat 连上来后暴露的语句,按规约分三类,逐类有结论:

| 类别 | 语句 | 处理 |
|---|---|---|
| **A. 有归属,等对应期次**(明确报错、不返回错数据) | `COUNT(*) ... UNION ...`、`SELECT DISTINCT ... LEFT JOIN ... GROUP_CONCAT(...)`、用户表上的 `ORDER BY` | 归 **P5**;当前返回 `1235` 并说明不支持 |
| **B. 无归属 / 卡住日常使用 → 并入 P4**(已补,规约 v0.1f G 组) | `LIMIT 0,1000`(分页偏移)原来报 `1064`;虚拟表多列 `ORDER BY` 原来报 `1235` | 已实现并通过 SC-342 / SC-343;`LIMIT <off>,<n>` / `LIMIT <n> OFFSET <off>` 两种写法等价,虚拟表多列排序按列序比较 |
| **C. 数据残留(不是 bug)** | `def` 库里有一张 `student`(table_id 16,2026-10-26 14:24 建)、`shop` 为空库 | 开发期用客户端建表留下的;要清可直接 `DROP DATABASE def` / `DROP DATABASE shop`(库非空会先要求删表) |

**边界仍然保住**:用户表上的 `ORDER BY` 现在返回

```
错误：用户表上的 ORDER BY 不支持(归 P5);虚拟表 information_schema.* 上支持多列 ORDER BY
```

—— 既让客户端可用,又没有把 P5 的能力偷偷提前。
