# tang_db 项目宪法

## 核心原则

### 一、分层边界唯一且不可穿透

系统只有两层:客户端层(FE)与数据层(BE)。两层之间**只**通过 `proto/` 下定义的 gRPC 服务通信。

- FE 不得直接读写 BE 的数据目录、不得直接碰任何数据文件。
- BE 不得包含任何查询语义、表结构、元数据或用户会话概念。
- 任何"为了省事直接读文件"的实现一律视为违规。

理由:FE/BE 分离是这个项目的骨架,边界一旦被穿透,后面加 SQL 层时整个结构就塌了。

### 二、不借外力(存储部分不可妥协)

BE 的存储引擎必须从零实现。**禁止**引入任何现成存储引擎或嵌入式数据库:
RocksDB、LevelDB、Badger、Pebble、SQLite、BoltDB、bbolt 及其任何绑定。

允许的依赖仅限:
- BE:Go 标准库、`google.golang.org/grpc`、`google.golang.org/protobuf`
- FE:`grpc-java`、`protobuf-java` 及常规构建/日志工具库

理由:这个项目的全部价值就在于亲手实现 memtable / WAL / SSTable / compaction。借了外力,就等于没做。

### 三、先日志后数据(崩溃安全不可妥协)

任何写路径的顺序固定为:

1. 追加 WAL 记录并 `fsync`
2. 更新 memtable
3. 向调用方返回成功

这个顺序不得调整。不得以"后台异步刷盘"为由跳过 `fsync`。

**已向调用方返回成功的写,在进程被 `kill -9` 之后必须仍然存在。**

### 四、可验证优先于"看起来对"

每个功能需求都必须有自动化测试覆盖。不接受"手工跑了一下,看起来没问题"作为完成证据。

凡声称"测试已通过",必须能给出实际的执行输出。禁止伪造测试结果。

### 五、接口先行

`proto/` 下的 IDL 先定稿,再实现两侧。两侧的桩代码由 `protoc` 生成,不得手写序列化/反序列化。

### 六、简单优先(YAGNI)

一期明确**不做**:SQL 语法、事务/MVCC、多节点与分布式、多版本快照隔离、二级索引、压缩算法调优、并发压测优化。

没写的代码不欠债。

## 技术栈约束(硬性)

| 项 | 取值 |
|---|---|
| 数据层 BE | Go 1.27,windows/amd64,模块名 `github.com/1638540149/tang_db/be` |
| 客户端层 FE | Java 17 + Maven 3.9.16,groupId `com.wangyu.tangdb` |
| 接口 | Protocol Buffers 3,IDL 位于 `proto/` |
| 默认数据目录 | `./data/BE`,可用启动参数覆盖 |
| 默认监听端口 | `:9100`(gRPC),可用启动参数覆盖 |

**本机构建注意**:开发机是 Windows 11,构建命令在 git-bash 下执行。
本机 `mvn`(sh 脚本版)不可用,必须调用 `mvn.cmd`。
Go 代理已配置为 `https://goproxy.cn,direct`。

## 开发流程与质量门

- 所有功能变更必须走 Spec Kit 链路(`specify → plan → tasks → implement`),不得跳过规约直接改代码。
- 测试必须真跑;禁止伪造输出。
- 每期验收必须在"杀进程后重启"这个动作上体现,而不是只跑单元测试。
- 一个可独立验证的改动一次提交,提交信息说清"做了什么 + 怎么验证的"。

## 治理

本宪法优先于其他一切实践。变更须写明理由并更新版本号。

所有实现与评审都必须核对是否符合本宪法;任何偏离必须在 `plan.md` 或 `tasks.md` 中显式声明并取得确认。
