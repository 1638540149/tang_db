> **本规约的作用**:把"P2 里一行数据能原子落盘"升级成"**一个事务要么全生效、要么全不发生,并且并发写不会互相覆盖**"。
> 这是全项目**风险最高**的一期:它同时改动 key 编码语义、WAL 记录格式、读路径与写路径。
> 状态为 **Draft**,评审通过后由项目所有者改成 Approved 才能施工。

## 1. 目标

一句话:**给库装上提交序号与快照 —— 一个事务的多次写入要么整体生效要么整体消失,并发改同一行时后到的那个会被明确拒绝而不是静默覆盖。**

P3 把 P2 的"单行写原子"抬到"事务原子":

1. **提交序号(commit_ts)** —— BE 一个全局原子计数器,提交时取号、写进 WAL 记录本身;序号只增不回退
2. **快照读(MVCC)** —— 事务开始时固定一个快照水位,读到的永远是"该水位下可见的最新版本";`key` 里那个 P2 写死的 8 字节版本段从此真正生效(**倒序存放**)
3. **原子批写(WriteBatch)** —— 一个事务的全部写入塞进**同一条 WAL 记录**,一次 fsync,要么全在要么全不在
4. **写写冲突检测** —— 提交时检查写集里每个 key 是否被"快照之后的其他事务"改过;是则报冲突、**整批不写、绝不静默覆盖**
5. **回滚是零成本** —— 未提交的写集只存在 FE 内存里,从未进过 WAL 与 memtable;`ROLLBACK` 就是丢掉它
6. **元数据的原子性** —— 建表/删表/TRUNCATE 的多条元数据记录进同一条批记录;P2 登记的 K26「半套元数据」口子由此关闭

**P3 的边界**:单机、**快照隔离(SI)**、不做跨表/跨机的分布式事务、不做 SSI(可串行化)、不做 savepoint、不做 compaction(承 P1/P2:segment 只增不合)。这些都要写清,否则 P4/P5 会来还债。

### 2.3 本期保证什么 / 不保证什么(必须写清楚)

| 事项 | P3 保证 | 不保证 |
|---|---|---|
| 单事务原子性 | 同一事务的全部写入同批生效;崩溃后要么全在要么全无 | 跨事务的原子性 |
| 提交成功的含义 | 返回 OK ⇔ 批记录已 fsync(`commit_ts` 就在记录里) | —— |
| 未提交数据 | **从未进过 WAL / memtable / segment**,天然不可见 | 不支持"未提交数据被我自己的其它会话看到" |
| 并发写同一行 | 快照之后被改过 → **报冲突,整批不写** | 不自动重试、不排队等待、不静默覆盖 |
| 读一致性 | 快照隔离:同一个事务内反复读同一行结果稳定;不出现脏读/不可重复读/幻读 | 不做 SSI,理论上仍存在写偏斜(write skew);不做跨事务的全序保证 |
| 序号 | 单调不回退、可跳号(空洞无害) | 不保证连续 |
| 事务隔离与崩溃 | 崩溃恢复后已提交事务全在、未提交全无、序号不回退 | 不保证"恢复过程中读到中间态"(恢复完成前不对外服务) |
| 数据格式 | 本期起数据目录格式版本 = 2;同版本内前后兼容 | **不兼容 P2 及以前的数据目录**(§5.4) |

## 3. 用户场景与验收(BDD)

### 场景 1:事务提交后数据可见

```
Given  BE 与 FE 都在运行
When   执行 BEGIN
And    执行 INSERT INTO t (id, name) VALUES (1, 'a')
And    执行 INSERT INTO t (id, name) VALUES (2, 'b')
And    执行 COMMIT
Then   返回提交成功,并给出 commit_ts
And    另一个会话 SELECT * FROM t 能查到两行
```

### 场景 2:回滚

```
Given  表 t 里已有 id = 1
When   执行 BEGIN
And    执行 UPDATE t SET name = 'changed' WHERE id = 1
And    执行 DELETE FROM t WHERE id = 1
And    执行 ROLLBACK
Then   返回"已回滚"
And    另一个会话读到的仍是原值(未提交数据从未落盘)
```

### 场景 3:事务内的读己之写

```
Given  表 t 里没有 id = 9
When   执行 BEGIN
And    执行 INSERT INTO t (id, name) VALUES (9, 'x')
And    执行 SELECT * FROM t WHERE id = 9
Then   返回这一行(本事务自己的写自己可见)
And    (另一个会话此时读不到它)
```

### 场景 4:★ 写写冲突(后到的被明确拒绝)

```
Given  两个 CLI 会话 A、B 都开着,表 t 有 id = 1
When   A 执行 BEGIN; UPDATE t SET name='A' WHERE id=1;   (还未提交)
And    B 执行 BEGIN; UPDATE t SET name='B' WHERE id=1;   (还未提交)
And    A 执行 COMMIT   → 成功
And    B 执行 COMMIT   → 失败
Then   B 得到明确报错:表 t 主键 1 写写冲突(请重试),不打印堆栈
And    数据库里是 A 的值 —— B 的写**没有**覆盖 A
```

### 场景 5:★ 快照隔离(同一事务内反复读稳定)

```
Given  表 t 里 id = 1 的 name = 'v1'
When   A 执行 BEGIN
And    A 读到 'v1'
And    B(另一个会话)UPDATE id=1 → 'v2' 并提交
And    A 再读一次
Then   A 两次读到的都是 'v1'(快照固定)
And    A 提交后新开的事务读到 'v2'
```

### 场景 6:★ 提交中途强杀 —— 四处注入点

```
Given  BE 配好 test_crash_point 并启动
When   在四个位置分别强杀:① 冲突检测后、写 WAL 前  ② WAL fsync 后、写 memtable 前
       ③ memtable 写完后、返回 OK 前  ④ 手工截断 WAL 尾部一条批记录
Then   ①②:该事务全部不可见(未提交)
And    ③:重启后该事务**全部可见**(OK 未返回但记录已落盘,按"记录完整即已提交"判定)
And    ④:该事务整体丢弃,服务正常启动,之前的数据完好
And    四种情况下:序号都**不回退**(重启后新事务的 commit_ts 大于崩溃前所有已提交序号)
```

> ③ 的口径要在验收报告里写清:客户端可能没收到 OK,但数据已持久化 —— 这是"提交成功 = 记录已持久化"的必然推论,也是 P3 明确接受的行为。

### 场景 7:★ 并发插不同行都能成功

```
Given  两个会话各自 BEGIN
When   A 插入 id = 101,B 插入 id = 102,各自提交
Then   两次提交都成功(冲突只发生在同一行的写写之间)
```

### 场景 8:★ 序号不回退(数据只在 segment 里的情形)

```
Given  memtable 阈值调小,写入若干事务后数据已刷进 segment,旧 WAL 已被回收
When   强杀 BE 并重启
Then   新事务取到的 commit_ts **大于**崩溃前任何已提交事务的 commit_ts
And    MANIFEST 里的 last_commit_ts ≥ 已落盘数据中的最大 commit_ts
```

### 场景 9:★ 元数据原子性与 DDL 中途强杀

```
Given  BE 在 test_crash_point 下运行
When   执行 CREATE TABLE(表记录 + 列记录 + 计数器三条元数据)并中途强杀
Then   重启后要么这张表完整存在(含全部列与主键),要么完全不存在
And    不得出现"表在、列缺"或"没有主键"这类半套元数据
And    若真的出现异常元数据,FE 启动必须**指名报错**(K26 保留为防御)
```

### 场景 10:P2 回归全绿

```
Given  P3 的改动已合入
When   bash scripts/p2-test.sh
Then   P2 的 11 个场景 + P2.1 的 12 条断言全部 PASS(52/52)
And    bash scripts/crash-test.sh → 1000 条随机 KV 强杀重启丢失 0 条
And    cd be && go build ./... && go vet ./... && go test ./... 全绿
And    cd fe && mvn.cmd test 全绿
```

## 4. 功能需求

### 4.1 接口(proto)

- **FR-301** 新增 `BeginTxn`:`BeginTxnRequest`(可选的 `read_only` 标记)→ `BeginTxnResponse{status, txn_id, snapshot}`。`snapshot` = **当前已提交水位**(当前最大已提交 `commit_ts`;空库为 0)。
- **FR-302** 新增 `CommitTxn`:`CommitTxnRequest{txn_id, snapshot, repeated Kv writes}` → `CommitTxnResponse{status, commit_ts, conflict_key, message}`。
- **FR-303** 新增 `AbortTxn`:`AbortTxnRequest{txn_id}` → `AbortTxnResponse{status,message}`。**只释放 BE 侧句柄,不产生任何 I/O**。
- **FR-304** `GetRequest` / `ScanRequest` 增加 `uint64 snapshot`:`0` 表示"最新已提交";否则按该快照返回可见版本。
- **FR-305** `ScanRequest` 的 `start_key` / `end_key` 语义改为**用户键级**(不含版本段):BE 按"去掉尾部 8 字节"后的用户键比较范围(见 §5.2)。
- **FR-306** `GetRequest.key` 语义为**用户键**(不含版本段);返回该用户键在快照下可见的版本值。
- **FR-307** `StatusCode` 增加 `CONFLICT = 5`;`CommitTxn` 冲突时返回该状态 + `conflict_key`(原始字节,**FE 负责翻译成表/主键**)。BE **不得**返回表名/列名/SQL(K22 的边界铁律)。
- **FR-308** `Put` 语义**保持不变**:BE 内部把它当成"单 key 自动提交事务"—— 自行取号、在 key 尾部追加版本段、走同一条批写路径。P1 的 `crash-test.sh` 必须继续可用(SC-210)。
- **FR-309** 批记录载荷上限:`max_txn_write_bytes`(默认 64MB)与写集条数上限(默认 100 万条);超限 → `INVALID_ARGUMENT` 并说明是哪一项超了。
- **FR-310** `proto/` 里仍然**不得出现表名、列名、SQL**(承 SPEC-P2 FR-104);本期新增字段全部是序号、快照与原始字节。

### 4.2 BE:提交协议(本期最核心的一组)

- **FR-311** 提交序号来自 BE 的**全局原子计数器**,取号时机 = **提交时**(不是事务开始时)。
- **FR-312** 一个事务的全部写入必须落在**同一条** WAL 记录里(类型 `TypeBatch`),顺序固定:**① 冲突检测 → ② 追加记录 → ③ fsync → ④ 写 memtable → ⑤ 返回 OK**。不允许先返回 OK 再落盘,不允许以"后台异步"为由跳过 fsync。
- **FR-313** `commit_ts` **写在批记录内部**;库中**不存在**第二个"提交状态"。一条记录完整(长度对得上 + CRC32C 通过)= 该事务已提交。
- **FR-314** fsync 成功后 BE 才写 memtable 并回 OK;OK 返回后进程被强杀,该事务**必然**存在。
- **FR-315** 记录尾部不完整或 CRC 不符(崩溃时的半条写)→ 恢复时**在断点处截断、整条丢弃**,服务照常启动;不得把"CRC 成功"当成提交判据(要凭**整条记录完整**)。
- **FR-316** 序号**单调不回退**:重启后取号 = `max(MANIFEST.last_commit_ts, 重放所见最大 commit_ts) + 1`;允许跳号,任何"序号连续"的假设都不允许出现在代码里。
- **FR-317** 取号后崩溃会留下**空洞**:空洞无害、不填补;`commit_ts` 只用于可见性大小比较。
- **FR-318** 单个事务的写入原子性**不依赖两阶段提交** —— 靠批记录的物理连续性直接获得。
- **FR-319** BE 侧事务句柄(`txn_id`)由 BE 单独发号(独立于 `commit_ts`,**不参与可见性**),仅作句柄与日志追踪用;FE 断开/`AbortTxn` 时释放。BE **不保存写集**(写集在 FE 内存)。

### 4.3 BE:读路径与版本可见性

- **FR-320** key 的末尾 8 字节是**版本段**,由 BE 独占维护:写入时填 `^commit_ts`(按位取反,大端),使**新版本字节序更小 → 排在前面**(设计 §7.1 的"倒序存放")。
- **FR-321** FE 传来的 key 一律**不含**版本段;BE 写入时追加,读取时按"去掉尾部 8 字节"得到用户键。BE **不解释**用户键的前几段是什么(仍然是原始字节,边界铁律不变)。
- **FR-322** 点查 `Get(user_key, snapshot)`:返回该用户键满足 `commit_ts ≤ snapshot` 的**最大**版本;墓碑也照原样返回(FE 解释为"不存在")。
- **FR-323** 范围扫描 `Scan(start, end, snapshot, ...)`:按用户键升序、每个用户键只输出**一次**(该快照下可见的那个版本);`start` 含、`end` 不含;同一用户键的多个版本必须在归并时分组消解。
- **FR-324** 扫描必须是**流式**的:每个数据源只保留当前一条记录;不得把整个范围或"某用户键的全部版本"整体读进内存(版本分组只允许在迭代器内部按需前进)。
- **FR-325** 快照可见性规则(INV-6):快照 `s` 读到的版本 = 满足 `版本.commit_ts ≤ s` 的**最大** `commit_ts` 版本;若不存在 → 该用户键对 `s` 不可见(等价"没有这行")。
- **FR-326** `snapshot = 0` 表示"最新已提交"(读当前水位);`Get`/`Scan` 的其它取值必须是 BE 曾发出过的快照号,乱填不导致崩溃或读到未来版本(按 `≤ s` 规则天然安全,但要在测试里固定这一行为)。
- **FR-327** 墓碑的可见性判定与正常版本**完全一致**:先按快照选出可见版本,再由 FE 判断它是墓碑。不得出现"墓碑优先于更新版本"这类错误。
- **FR-328** 读路径**不触碰 WAL**,也不因并发写入而阻塞(memtable 跳表支持并发读)。

### 4.4 BE:写写冲突检测

- **FR-329** 提交时对写集中**每个** key 检查:"该用户键**最新已提交版本的 commit_ts** 是否 > 本事务的 snapshot";是 → 冲突(说明快照之后有人改过它)。
- **FR-330** 冲突时**整批不写**:不追加 WAL、不改 memtable、不取 `commit_ts`;返回 `CONFLICT` + 第一个冲突的 key(顺序按写集顺序,保证可复现)。
- **FR-331** 冲突检测必须覆盖**墓碑版本**:"最新已提交版本是墓碑"同样算被改过。
- **FR-332** 检测的原子性:同一批的冲突检测 + 取号 + 追加 WAL 必须在**串行区间**内完成(同一时刻只能有一个批在"检测→fsync"这段里推进),否则两个并发事务可能都检测通过而互相覆盖。
- **FR-333** 冲突信息:**BE 只回 key 的原始字节**;FE 负责翻译成「表 t 主键 x 写写冲突」。
- **FR-334** 并发**不同**用户的写必须能并行推进(不能因为"检测串行"就把整个写路径变成单线程瓶颈);同一时刻多个事务可以向同一个 memtable 写(多写者)。

### 4.5 BE:序号与 MANIFEST 的持久性义务

- **FR-335** `MANIFEST` 增加 `format_version`(本期 = 2)与 `last_commit_ts` 两个字段。
- **FR-336** 每次 flush 产出新 segment、以及每次启动(恢复完成)时,MUST 保证 `MANIFEST.last_commit_ts` ≥ **本次已落盘数据中的最大 `commit_ts`**。
- **FR-337** 违反 FR-336 的后果是**序号回退**(旧版本会"看起来比新版本新",属最危险的一类 bug),必须有专门用例覆盖(WAL 已被回收、数据只在 segment 里的恢复路径)。
- **FR-338** 恢复顺序承 P1:读 CURRENT → MANIFEST → 校验并加载 segment(缺文件跳过并告警)→ 重放 WAL(CRC 逐条) → 计算 `next_commit_ts` → 才对外服务。
- **FR-339** 恢复期间不得对外提供读写(端口在恢复完成后才就绪,承 P1 行为)。

### 4.6 FE:事务状态机与 CLI

- **FR-340** 新增语句 `BEGIN` / `COMMIT` / `ROLLBACK`(大小写不敏感)。`BEGIN` 时向 BE 取快照;`COMMIT` 走 `CommitTxn`;`ROLLBACK` 丢弃写集并 `AbortTxn`。
- **FR-341** 一个 CLI 会话内**最多一个**事务:已在事务中再 `BEGIN` → 报错"已有活动事务";无事务时 `COMMIT`/`ROLLBACK` → 报错"没有活动事务"。
- **FR-342** 事务内的 DML 只改**内存写集**:按 key 覆盖(同一事务多次改同一行只保留最终版本,不留中间版本);`SELECT` 先看写集再看 BE(读己之写)。
- **FR-343** 事务外的单条 DML 自成事务(自动提交:取快照 → 写 → 提交);事务外的 `SELECT` 使用"最新已提交"快照。
- **FR-344** 事务内语句执行失败**不自动回滚**:事务保持活动,由用户决定继续还是 `ROLLBACK`;错误信息要说清"事务仍在进行中"。
- **FR-345** CLI 断开(EOF / `exit`)时:有活动事务 → 丢弃写集、`AbortTxn`,并打印明确提示。
- **FR-346** 事务活动期间 CLI 提示符必须能看出状态(如 `tangdb(txn)>`),便于并发测试观察。
- **FR-347** `ROLLBACK` 后读到的数据必须与 `BEGIN` 前完全一致(未提交数据从未落盘,所以这是天然成立的 —— 必须有测试固化它)。
- **FR-348** 提交成功后要能给出 `commit_ts`(CLI 显示,或至少日志可见),便于验收与排查。

### 4.7 FE:key 编码与范围边界(改动最危险的一处)

- **FR-349** FE 的 key 编码只产出四段:表 ID(4B 大端)+ 索引 ID(4B 大端)+ 索引列值(主键保序编码)+ 主键值(主键索引为空);**不得再拼版本段**(P2 的"固定写 0"删除)。
- **FR-350** 范围条件(主键等值/范围)以**用户键**表达:`start` 含、`end` 不含;`pk > v` 用"用户键前缀 + 1 字节"表达(承 P2 思路),**不得**再依赖"8 字节零 + 1 字节"这类与版本段形态绑定的哨兵。
- **FR-351** FE 侧任何地方都不得假设"版本段的字节内容"(它由 BE 维护);FE 只按用户键比较与拼接。
- **FR-352** 主键冲突(语义级):事务快照下该主键可见版本存在且**非墓碑** → 报"主键冲突(表 t,主键 x)"且不覆盖;可见版本是墓碑 → 允许插入。
- **FR-353** 同一事务内对同一主键先删后插、先插后删等组合,按"写集里最后一次操作胜出"处理,不得出现两条记录同时生效。
- **FR-354** UPDATE 的列范围仍**只允许非主键列**(承 SPEC-P2 K19);改主键 = 删 + 插,留 P4 之后。

### 4.8 FE:元数据原子性

- **FR-355** 从 P3 起,`CREATE TABLE` / `DROP TABLE` / `TRUNCATE TABLE` 的**全部**元数据记录(表记录 + 全部列记录 + `sys_counters` 更新)必须在**同一条批记录**里原子生效。
- **FR-356** 启动时的元数据校验(承 SPEC-P2 FR-117 / K26)继续保留,作为**防御**手段:异常元数据仍然要指名牌报错,不得静默忽略或自动修补。
- **FR-357** DDL 不允许在显式事务内执行:事务中执行 DDL → 报错"DDL 不能在事务内执行,请先 COMMIT 或 ROLLBACK"(见 K45)。
- **FR-358** catalog 的内存缓存仍是"最新已提交"视图:任何已提交的 DDL 立刻对所有会话可见(承 K27);本期不做会话级 catalog 快照。

### 4.9 错误提示(全中文)

- **FR-359** 冲突:`表 t 主键 x 写写冲突(该行在本事务开始后被其它事务修改,请重试)` —— 不含堆栈,不含内部 key 十六进制(除非用户显式要求诊断)。
- **FR-360** 事务状态错误:重复 `BEGIN`、无事务 `COMMIT`/`ROLLBACK`、事务内 DDL,各有明确文案。
- **FR-361** 超限:`事务写入量超过上限(64MB)` / `事务写入条数超过上限(1000000 条)`。
- **FR-362** 格式不兼容(§5.4):`数据目录格式版本 1 与本期(2)不兼容:请清空数据目录后重启`。
- **FR-363** 任何错误都不打印 Java 堆栈(承 SPEC-P2 FR-173);BE 侧错误必须带具体原因(不吞错)。

### 4.10 配置

- **FR-364** `config/be.conf` 新增:`test_crash_point`(默认空;取值 `before_wal` / `after_fsync` / `after_memtable` / `before_ok`;命中一次即让 BE 进程立即退出,模拟强杀)、`max_txn_write_bytes`(默认 `64MB`);`config/fe.conf` 新增:`heartbeat_enabled`(默认 `true`,见 FR-367)。沿用 P1 的配置解析与校验(未知项报错、非法取值报错)。
- **FR-365** `test_crash_point` 必须在启动日志里**明显告警**(如 `WARN 崩溃注入已启用:after_fsync(仅验收使用)`),并在 README 里说明它的用途与风险。

### 4.11 会话与多实例(顺带关闭 P2 §11 的两个缺口)

> 这两条不是"锦上添花":**不做 FR-367 就开不出两个并发的 CLI 会话,SC-202 / SC-207 根本无法验收**;不做 FR-368 则 P3 测试期间(要频繁重启 BE)`SHOW BACKENDS` 会长期为空,掩盖真实问题。

- **FR-366** 心跳监听不再是硬约束:`heartbeat_enabled = false` 时,FE **不绑定**心跳端口,也不启动 FE 侧 gRPC 服务;SQL 功能完全不受影响。
- **FR-367** `heartbeat_enabled = false` 的会话执行 `SHOW BACKENDS` → 明确提示 `本会话未启用心跳监听(heartbeat_enabled = false),看不到 BE 状态`,**不得**报"BE 不可用"或返回空表。
- **FR-368** FE 收到**未登记过**的 `be_id` 心跳时**隐式注册**(自动登记为可用),并在日志里记录一次;因此 FE/CLI 重启后不需要重启 BE 也能重新看到 BE 状态(关闭 P2 §11 的 G2)。

- **FR-370** 并发验收(SC-202/SC-207)必须用 `heartbeat_enabled = false` 起第二个及以后的 CLI 会话;`scripts/p3-test.sh` 要把它写进脚本,并**在报告里写明**哪个会话持有默认心跳端口。

## 5. 数据与格式

### 5.1 key 编码(版本段终于真了)

```
┌──────────┬────────────┬──────────────────┬────────────────┬────────────────┐
│ 表 ID    │ 索引 ID    │ 索引列值          │ 主键值          │ 版本号         │
│ 4B 大端  │ 4B 大端    │ 主键保序编码      │ (主键索引为空)  │ 8B 大端 ^ts    │
│ ← FE 编码 ──────────────────────────────────→ │ ← BE 维护 ──→ │
└──────────┴────────────┴──────────────────┴────────────────┴────────────────┘
```

- **版本段 = `^commit_ts`**(按位取反、大端),因此**新版本字节序更小、排在前面**:读最新 = 读第一条,按快照读 = 从前找第一条 `ts ≤ 快照` 的。
- `commit_ts` 是全局单调递增的 `uint64`,`^ts` 全 1(即 `ts = 0`)的版本排在**最后**(最旧)。
- 上面这条同时决定了**范围边界的写法**:FE 不再用"8 字节零 + 1 字节"的哨兵(它只对"版本段全 0"成立),范围一律以**用户键**表达(FR-350)。

### 5.2 读路径的用户键分组

```
BE 看到的 key:  [用户键 ............][版本 8B]
                └─ 不解释,只当字节 ─┘└ 分组依据 ┘

Scan 请求:      start_key / end_key = 用户键(FE 语义),snapshot = s
BE 归并:        按用户键分组(多路归并),每组只输出 max{ts ≤ s} 的那一条
返回:           [用户键+版本][value]  —— FE 自己剥掉尾部 8 字节再解释 value
```

### 5.3 WAL 记录格式(P3 起)

```
┌─────────┬──────┬────────────┬───────────────────────────────────────────────────────┐
│ CRC32C  │ Type │ PayloadLen │ Payload                                                │
│ 4B      │ 1B   │ 4B 小端    │ commit_ts(8B) │ txn_id(8B) │ kvCount(4B) │ [klen|k|vlen|v]×n │
└─────────┴──────┴────────────┴───────────────────────────────────────────────────────┘
Type = BATCH(2):P3 起所有写入(Put 也不例外);Type = PUT(1) 仅保留"只读解析"能力(读 P1 老 WAL)
CRC32C 覆盖 Type + PayloadLen + Payload(与 P1 一致,不变)
```

- **`commit_ts` 在记录里**,这是"已提交"的唯一判据(FR-313)。
- `txn_id` 只用于排查与审计,**不参与**提交判定;值为 0 表示"自动提交的单 key 写"。
- 批记录的 `klen/k` 中的 key **含版本段**(BE 已追加)。
- `MANIFEST` JSON 新增:`format_version`(2)、`last_commit_ts`;其余字段(`segments` / `next_segment` / `next_wal`)不变。

### 5.4 格式版本与老数据(必须正面回答"向后兼容")

- **不兼容 P2 及以前的数据目录**,理由:P2 把版本段固定写成 `0x00×8`,而本期语义是 `^commit_ts`(新版本字节序更小)。二者混在一棵 LSM 里,老数据会被当成"最旧的版本"(语义上正确)同时又是**字节序最小的**(会被误判成最新) —— 混用会产生**静默的可见性错误**,这是不能接受的。
- 因此:**启动时若 `MANIFEST` 的 `format_version` 缺失或 ≠ 2,BE 启动失败并报 FR-362 的明确错误**,要求清空数据目录;空目录首次启动时写入 `format_version = 2`。
- 影响面:P1/P2/P2.1 的**测试数据**需要丢弃(都是可重建的测试数据);`scripts/p2-test.sh` 与 `scripts/crash-test.sh` 本来就会清空各自的数据目录,不受影响;日常 `data/BE` 目录需要手工清一次(README 里写明)。
- 值编码(行/墓碑)**不变**(SPEC-P2 §5.3 原样):版本住在 key 里,不在 value 里。

## 7. 关键技术决策(本期默认值)

已按推荐取值,写进规约作为施工默认。**有异议请指出,没异议就照办。**

| # | 决策点 | 取值 | 理由 |
|---|---|---|---|
| K39 | 提交序号谁发、何时发 | BE 全局原子计数器,**提交时**取号 | 设计 §6.2.1 定的;取号早于提交会制造大量无谓空洞 |
| K40 | 快照口径 | `snapshot` = 事务开始时的**当前已提交水位**;本事务的写通过写集覆盖实现"读己之写" | 与设计 §8.1 一致;不需要额外的"自己事务号"参与可见性 |

| K42 | 可见性判定 | 每用户键取 `max{ts ≤ snapshot}`;墓碑与正常版本同规则;`snapshot=0` = 最新 | 设计 §8.1.1 的读规则 |

## 8. 验收标准

| 编号 | 验收项 | 判定 |
|---|---|---|
| **SC-201** | 事务语义 | BEGIN / COMMIT / ROLLBACK 行为与 §3 场景 1~3 一致;回滚后数据与事务前完全一致 |

| **SC-203** | 崩溃注入(前两处) | `before_wal` 强杀后该事务**全部不可见**;**`after_fsync` 强杀后该事务**全部可见** —— 记录已完整落盘即已提交(与 FR-313/FR-315、场景 6③、设计方案 §6.2.1 一致)。<br>⚠️ 原措辞把两处都写成"不可见",与 FR 自相矛盾,2026-10-23 由 **I6** 修正(实现方按 FR 执行,未按错误措辞丢弃已 fsync 的完整记录) |
| **SC-204** | 崩溃注入(第三处) | `after_memtable` 强杀后,重启该事务**全部可见**(记录已落盘即已提交),口径写进验收报告(场景 6 ③) |
| **SC-205** | WAL 尾部截断 | 手工截断尾部一条批记录 → 该事务整体丢弃、服务正常启动、之前数据完好(场景 6 ④) |

| **SC-207** | 快照可见性(INV-6) | 同一主键三版本 + 多档快照(15/20/25/30 对拍,按设计 §8.1.1 的表);长事务挂住时并发写不影响它读数(场景 5) |

## 9. 边界与异常清单

| 情形 | 期望行为 |
|---|---|
| 无事务时 `COMMIT` / `ROLLBACK` | 报"没有活动事务" |
| 事务中再 `BEGIN` | 报"已有活动事务,请先 COMMIT 或 ROLLBACK" |
| 事务内执行 DDL | 报"DDL 不能在事务内执行"(K45) |
| 事务内语句语法错/表不存在 | 事务**保持活动**;错误提示里说明事务仍在进行 |
| 事务内先删后插同一主键 | 写集最后一次操作胜出;不得两条同时生效 |
| 提交时写集为空(只读事务) | 直接返回成功(可以不取号);不得报错 |
| 提交时冲突 | 整批不写;回 `CONFLICT` + 冲突 key;FE 报中文冲突错误 |
| 同一批里多个 key 都冲突 | 报**第一个**(按写集顺序)冲突的 key,保证可复现 |
| `commit_ts` 溢出 uint64 | 不处理(实际不可达),但代码里不得用有符号比较 |
| 快照号乱填(大于当前水位) | 行为安全(按 `≤ s` 取不到未来版本);测试固化为"不会读到未来数据" |
| 快照号是未来的墓碑 | 返回"该行存在"的旧可见版本(墓碑只对 `≥ 其 ts` 的快照生效) |
| 事务写集超 64MB / 100 万条 | 报超限错误;不写任何数据 |
| WAL 记录尾部截断(半条) | 整条丢弃;之前记录完好;服务能启动 |
| WAL 记录 CRC 不符 | 同上(在断点截断) |
| 数据目录是老格式(无 `format_version` 或 = 1) | 启动失败并报格式不兼容,要求清空数据目录(FR-362) |
| `MANIFEST.last_commit_ts` 小于重放所见最大序号 | 取**较大**者 + 1(不报错,但要在日志里告警:说明有过一次非正常退出) |
| 恢复完成前有客户端连接 | 端口未就绪,连接失败(承 P1 行为) |
| BE 不可用时开事务 | 报"BE 不可用(含地址与最后心跳时间)",不挂起 |
| `test_crash_point` 在非空值下启动 | 启动日志明显告警;README 说明仅验收使用 |
| CLI 在有活动事务时被强杀 | 未提交写集丢失(这是正确行为);BE 侧句柄过期无害 |
| 同一行被 A 提交、B 提交(快照相同) | 先到的成功,后到的报冲突(场景 4) |
