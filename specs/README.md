下面是**外部评审(2026-10-22)提出的、需要对应期次正面回答的必答项**,立规约时必须逐条给出协议或结论:

| 必答项 | 归属期次 | 问题 |
|---|---|---|
| WAL 提交协议:**WAL 记录完整 ≠ 事务已提交** | **P3** | 事务写了 WAL、刷盘了、但提交状态没落盘就崩了 —— 重启后靠什么判定该重放还是该丢弃?需明确 `txn_id` / `commit_ts` / WAL 中独立的 **COMMIT 记录** / 未提交数据的恢复处理;不得只凭 CRC 成功就认定已提交 |
| MVCC 版本模型的细节 | **P3** | 快照水位取自"已提交序号"而非事务 ID;并发提交的序号分配;同事务多次改同行是否留中间版本;二级索引与主键在同一 WriteBatch 生效;长事务期间 Compaction 的版本保留水位;恢复后事务序号如何续增而不冲突 |
| 点查路径**行级定位** | **P5**(读路径优化) | 现状(P1~P4):ZoneMap 逐 chunk 过滤 → 命中 chunk 解 key 列 → 块内线性查找,**没有行级索引**。待补:Index Block 按 chunk 首 key 二分、块内偏移数组/二分、块级布隆过滤 |
| HNSW 在**过滤条件下的召回** | **P7** | 先取每段 Top-K 再按 MVCC/条件过滤会返回不足 K 条;需"可迭代候选扩展"而非固定放大 1.5K,并以暴力精确检索为基准,按删除率/更新率/段数/过滤选择率做召回矩阵 |
| 推理下推的**幂等与副作用** | **P7** | 数据库可回滚自己的写入,但撤不掉已经完成的外部推理调用;需批次 ID、幂等键、内容哈希缓存、超时与重试上限、模型版本与维度校验、外部服务不可用时的行为 |
| 混合查询的**语义先行** | **P6/P7** | 顺序定为:精确向量检索 → ANN → CBO 选路;并明确"先过滤后检索"的受限图遍历、"先检索后过滤"的候选扩展量、统计信息过期时的保守回退、ANN 近似结果的对外说明、小表/低选择率直接暴力计算的阈值 |

> P2 规约(SPEC-P2)不包含这两项:Web 控制台的库表树与自身状态**依赖 P2 才有的 catalog 与心跳**,但界面本身落 P8;生态接入落 P9、全文检索落 P10。

## 每期验收前的自查表(八维,来源:行业评审框架)

每期交付前逐维自查一遍,结论写进该期验收报告;哪一维答不上来,就说明那期没做完:

| # | 维度 | 自查问题 |
|---|---|---|
| 1 | 定位与差异化 | 这期做完,库比上期多了什么**别人没有的**能力? |
| 2 | 整体架构 | 模块边界有没有被穿透(FE 碰数据文件 / BE 懂表名 SQL)? |
| 3 | 存储与索引 | 数据组织、持久化结构、索引是否可靠?文件格式改动是否向后兼容? |
| 4 | 事务与可靠性 | 崩溃闭环还在吗(杀进程后已提交数据零丢失)? |
| 5 | 查询执行 | 解析 → 计划 → 执行 → 结果,这条链是否完整且可解释? |
| 6 | 性能验证 | 延迟/吞吐/恢复/内存/写放大读放大,哪些测了、哪些没测? |
| 7 | 工程化与产品化 | 一键脚本、文档、错误提示、可观测性是否跟得上? |
| 8 | 开发路线 | 哪些该保留、哪些是当前不必要的复杂度、下一期优先做什么? |

## 维护规则

1. 一期一份规约,文件名为 `P<n>-<slug>.md`。
2. 规约变更须升版本号并写变更记录,不得静默修改。
3. 状态由你(项目所有者)确认后变更;**起草方不得自行把 Draft 改为 Approved**。
4. 实现过程中发现的规约缺口,记入该规约的「待补充」区,由你确认后合并进正式条目。
