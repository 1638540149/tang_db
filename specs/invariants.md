# tang_db 内核不变量与故障注入验收清单

> 这份清单回答一个问题:**"功能跑通了"不等于"内核可信"。** 它把散在设计文档各处的承诺,收敛成一组**必须成立的不变量**,以及**怎么证明它成立**。
>
> 用法:每期验收时逐条打勾(与 `specs/README.md` 的八维自查表配合使用),结论写进该期验收报告。任何一条"当前期次应当成立却发现不成立"的,该期不算完成。
>
> 来源:三轮外部评审(2026-10-22)与本项目自身设计文档 v1.5 §§6/8/9/14/18。**这是过程材料,不入库。**

---

## 0. 一句话总纲

真正要证明的不是"功能列表有多完整",而是:

> **在并发写入、进程崩溃、重启恢复、后台 Compaction 同时存在的情况下,数据依然正确。**

本机是 Windows,杀进程统一用 `taskkill /F`(脚本内已封装);崩溃注入一律指"不给进程任何清理机会的强杀"。

## 2. 每期的故障注入动作(可执行)

| 期次 | 注入什么 | 期望 |
|---|---|---|
| P1 | 写入中途 `taskkill /F` BE;WAL 尾部截断;删掉 MANIFEST 引用的 segment | 已返回 OK 的数据零丢失;服务能起来;缺失文件跳过并告警 |
| P2 | 建表 / 删表 / TRUNCATE **各阶段**强杀;强杀 FE 与 BE 后重启 | 元数据异常被明确报出(指名表 + 给出系统表 `table_id` 与 key 前缀);不静默、不自动重建;正常元数据重启后可继续读写 |
| P3 | 提交前 / WAL 刷盘后 / memtable 写完后 / 批记录尾部截断 四处强杀 | 已提交的全在、未提交的全无;序号不回退;主键与索引一致 |
| P3/P4 | 并发会话改同一行;随机写改删后用索引路径对账 | 冲突被报出而非静默覆盖;索引与数据零不一致 |
| P5 | compaction 与写入、查询并发进行;compaction 中途强杀 | 有效版本不丢;并发新写入不被覆盖;正在跑的查询不受影响 |
| P7 | 向量列写入中途强杀;HNSW 参数/过滤逻辑改动 | 索引与向量数据一致、重启可用;Recall@K 不回退 |

## 3. 观测口径(没有数字就不算验过)

崩溃与并发测试之外,以下指标**从 P1 起就记录**(先不设门限,P5 起生效):

- 写放大:写入 5GB 有效数据后,数据目录总增长 / 有效数据量
- 读放大:`chunk_reads`(点查读取并解码的 chunk 数)、`key_compares`(块内平均比较次数)、`bytes_read`(单次查询实际读取字节数)
- 内存峰值:导入与查询期间进程峰值 RSS
- 恢复时间:100 万行数据的启动恢复耗时

> 报数必须同报条件(机器/数据/负载/缓存/统计口径/向量参数/是否含后台任务),模板见设计文档 §18。

## 4. 违反任何一条时怎么记

1. **停下当前期次** —— 先修不变量,再谈加功能
2. 在设计文档对应章节旁写明违反的具体表现与修复方式(不写"已修",写"为什么原来会错")
3. 在 `specs/P<n>-*.md` 的「待补充」区登记,由项目所有者确认后并入正式条目
4. 如果某条不变量在当期**根本不该成立**(如 P1 没有 MVCC),在验收报告里写清"不适用 + 归属期次",不留空
