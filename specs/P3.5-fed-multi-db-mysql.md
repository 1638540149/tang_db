## 1. 目标

P3.5 一期做三件事,顺序固定:

1. **第零步 · FE 变成常驻服务**(决策 D20):`fed` 常驻,持有**唯一的 catalog 权威缓存**与会话层,负责监听协议端口与心跳端口;`cli` 退化为**瘦客户端**,通过协议连 `fed`。这一步同时关掉两个已登记缺口:**跨进程 DDL 不可见**、**心跳端口被 CLI 抢占**。
2. **第一步 · 库命名空间**(决策 D19):`CREATE / DROP DATABASE`、`USE <db>`、限定名 `db.tbl`;表名唯一性变为**库内唯一**,**表 ID 仍全局唯一** → **BE 与 key 布局零改动**。
3. **第二步 · MySQL 协议**(接口 I-01):官方 `mysql` 客户端、JDBC、图形客户端(DataGrip / Navicat)直连执行 SQL。范围限定为**可测子集**,不承诺兼容整个 MySQL。

**为什么三期合成一期**:三件事都动 FE 的**会话与名字解析层** —— 先有常驻 FE 才有地方挂协议监听,先有多库,协议的 `COM_INIT_DB` 与连接参数 `database` 才有去处。拆开做会返工三遍。

**做完能看到什么**:起 BE → 起 `fed` → CLI / `mysql` / DataGrip / JDBC 同时连上,**一个会话建的表在另一个会话立刻可见**;`CREATE DATABASE shop` → `USE shop` → 建表,切回 `default` 看不到它。

## 2. 范围

### 2.1 本期做(三步)

**第零步 · 常驻 FE 与会话层**

| 编号 | 内容 |
|---|---|
| S0-1 | `fed` 常驻进程:持有唯一 catalog 权威缓存、会话表、执行入口;监听**协议端口**与**心跳端口** |
| S0-2 | 会话层:每连接一个会话,会话内独立的**当前库 / 当前事务 / 写集**;会话内语句串行,会话间并发 |
| S0-3 | CLI 改为**瘦客户端**:连 `fed`,不再自带 FE、不再直连 BE |
| S0-4 | 启动形态与脚本:BE → `fed` → 客户端;启动/停止只有两个脚本 `scripts/start-be.sh`、`scripts/start-fe.sh`(均支持 `--daemon` 与 `stop`),`start-fe.sh cli` 起客户端(接口 I-10 一并落地) |
| S0-5 | 会话上限、空闲超时、优雅退出;`SHOW SESSIONS` 能看当前会话 |

**第一步 · 多库命名空间**

| 编号 | 内容 |
|---|---|
| S1-1 | `CREATE DATABASE` / `DROP DATABASE` / `USE` / `SHOW DATABASES` |
| S1-2 | 限定名 `db.tbl`(DML 与 DDL 都可用);未限定 = 当前库 |
| S1-3 | 默认库 `default`,始终存在、不可删 |
| S1-4 | 表名唯一性 = **库内唯一**;表 ID 仍**全局唯一**(不按库分段) |
| S1-5 | 库元数据持久化:`sys_databases`(走系统表保留区,**先领号**) |
| S1-6 | `sys_tables` 增"所属库"列;老数据目录**宽容读**(缺列视为 `default`),**key 布局不变** |
| S1-7 | 系统表 ID 登记表落地:新模块领号、不提前建空表、`next_table_id` 新建库从 64 起、校验改为"不在登记表内即用户表" |

**第二步 · MySQL 协议**

| 编号 | 内容 |
|---|---|
| S2-1 | 握手 v10 + `mysql_native_password` 认证 + 能力位协商 + 字符集 `utf8mb4` |
| S2-2 | 命令:`COM_QUERY` / `COM_INIT_DB` / `COM_PING` / `COM_QUIT` |
| S2-3 | 文本结果集(列定义 + 行 + EOF)、`OK` / `ERR` 包、错误码按接口 I-03 对齐 |
| S2-4 | 连接期兼容语句白名单(客户端连上来会先发一堆 `SET` / `SELECT @@xxx`,必须接受并给合理响应) |
| S2-5 | 事务:`BEGIN` / `COMMIT` / `ROLLBACK` 经 `COM_QUERY` 执行;会话在事务中时置 `SERVER_STATUS_IN_TRANS` |
| S2-6 | 三类客户端实测:官方 `mysql` 客户端、JDBC(`mysql-connector-j`)、图形客户端(DataGrip 或 Navicat) |

### 2.2 本期明确不做(及归属)

| 不做 | 归属 / 理由 |
|---|---|
| **TLS / SSL** | 不做。本期内网明文口径,连接串必须显式 `useSSL=false`;要上 TLS 需另立决策(破例:需引证书库或自实现,成本单独立项) |
| **服务端预编译** `COM_STMT_PREPARE` / `EXECUTE` / `CLOSE` | 不做。连接串需 `useServerPrepStmts=false`(Connector/J **默认即客户端预编译**,发的是 `COM_QUERY`,所以默认能连上);收到该命令回明确错误(见 FR-449) |
| `caching_sha2_password`(MySQL 8 默认认证) | 不做。只提供 `mysql_native_password`(见 §6 第 3 条:为什么这样选更省事) |
| 权限 / `GRANT` / `REVOKE` | P13(决策 D16 未拍板前不施工) |
| 多 `fed` 集群 / 连接池 / 负载均衡 / 故障转移 | 不做。单 `fed` 单进程 |
| 存储过程 / 触发器 / 事件 / 游标 | 不做,且不在期次表内 |
| `LOAD DATA`、`SHOW` 全家族、`SET GLOBAL`、`COM_CHANGE_USER` | 不做;只做 S2-2 与白名单里的子集 |
| `information_schema` / `performance_schema` 完整实现 | **待拍板(§12 I9)**:推荐只做最小只读视图(`SCHEMATA` / `TABLES` / `COLUMNS`),其余返回空结果集或明确错误 |
| 跨库单条 SQL(一条 SQL 里引用两个库的表、跨库 JOIN) | 不做。本期 JOIN 本身尚未实现(P5/P6),跨库会先把语义搞乱 |
| 跨库事务(一个事务写两个库) | 不做。**但要注意**:本期多库下"一个事务写同一个库的多张表"是允许的(表 ID 全局唯一,BE 不区分库) |
| 查询超时 / 结果集大小限制 / 慢查询 | P8(接口 I-05)。本期协议层只做**单包分帧**,不做超时 |
| 库级字符集 / 排序规则 | 不做,统一 `utf8mb4`(见 K71) |

## 3. 用户场景与验收(BDD)

### 场景 1 · 多客户端看到同一份 catalog(**本期的核心收益**)

- **给** 一个正在运行的 `fed`,它已经连着 BE
- **当** 会话 A(CLI)执行 `CREATE TABLE t(a INT PRIMARY KEY)` 并提交
- **那么** 会话 B(另一个 CLI)**立刻**看到 `t`(不需要重连),`SHOW TABLES` 里有它
- **验收方式**:两个 CLI 长驻,交替执行;关掉 P2/P3 遗留的"跨进程 DDL 不可见"缺口
- **反例(必须不再出现)**:B 报"表不存在",直到 B 重启

### 场景 2 · 三个客户端同时在线

- **给** `fed` 已启动
- **当** 官方 `mysql` 客户端、一个 JDBC 程序、DataGrip 同时连上
- **那么** 三者各自有独立会话(当前库、事务互不干扰),都能执行同一组 SQL
- **验收方式**:三者并发跑,`SHOW SESSIONS` 能看到 3 个会话

### 场景 3 · 多库基本闭环

- **给** 空库(fresh data_dir)
- **当** 依次执行 `CREATE DATABASE shop;` → `USE shop;` → `CREATE TABLE orders(...)` → `INSERT ...` → `USE default;` → `SHOW TABLES;`
- **那么** `shop.orders` 可查、`default` 里**没有** `orders`;`SHOW DATABASES` 列出 `default` 与 `shop`
- **验收方式**:脚本化,逐条断言

### 场景 4 · 限定名与同名表

- **给** `default` 与 `shop` 两个库
- **当** 两个库各建一张同名表 `t`(不同结构),再用 `shop.t` / `default.t` 访问
- **那么** 两者互不影响,限定名取到正确的表;同一库里重名建表报错
- **验收方式**:断言列结构不同、数据不串

### 场景 5 · 库级 DDL 的边界

- **给** `shop` 库里有表
- **当** `DROP DATABASE shop;`
- **那么** **拒绝**并提示"库非空,请先删表"(本期不做级联删除);删掉表后再 `DROP` 成功
- **当** `DROP DATABASE default;`
- **那么** 拒绝(`default` 不可删)
- **当** `USE nosuchdb;` / `CREATE DATABASE shop;`(已存在)
- **那么** 分别是"未知库 1049" / "库已存在 1007",错误可读

### 场景 6 · 老数据目录不返工(升级路径)

- **给** 一个 **P3 期间产生**的数据目录(表都归属旧语义的"唯一空间",`sys_tables` 里没有库列,`next_table_id` 是 16 或更大)
- **当** 用 P3.5 的 `fed` 启动
- **那么** 老表**全部可用**,一律视为 `default` 库的表;key 布局不变、数据一条不丢;新建表时表 ID 从 64 起
- **反例(必须不再出现)**:启动即报"元数据非法",或老表 ID 被当成系统表、或新表 ID 与老表撞号

### 场景 7 · 官方 mysql 客户端直连

- **给** `fed` 已启动,协议端口已监听
- **当** `mysql -h 127.0.0.1 -P <port> -u <user> -p -D shop`
- **那么** 能执行 `SELECT` / `INSERT` / `BEGIN; ... COMMIT;` / `USE` / `SHOW DATABASES`;语法错返回 `1064`、表不存在 `1146`、唯一冲突 `1062`
- **验收方式**:真实客户端 + 真实输出贴进验收报告

### 场景 8 · JDBC 直连

- **给** 一个最小 JDBC 程序(连接串按 K66 写)
- **当** 它执行同一组 SQL(含事务与切库),并处理一个异常(捕获 `SQLException`,检查 `getErrorCode()`)
- **那么** 全部正确;错误码与场景 7 一致
- **反例(必须不再出现)**:连接挂在握手阶段、或报"Unknown system variable"、或 `useServerPrepStmts` 默认值导致语句执行失败

### 场景 9 · 图形客户端直连

- **给** DataGrip 或 Navicat
- **当** 新建连接(明文、`useSSL=false`)并执行一组 SQL、跑一次切库
- **那么** 连得上、能建表、能查询、错误提示可读
- **口径**:图形客户端的"树形导航/自动补全"依赖 `information_schema`,本期是否实现见 §12 I9 —— **未实现时,只有导航功能不可用,执行 SQL 必须正常**,这一条必须写进验收报告(不许含糊)

### 场景 10 · `fed` 重启与客户端行为

- **给** 三个已连接的客户端,其中一个持有未提交事务
- **当** `fed` 重启
- **那么** 三个连接都断开;持有未提交事务的会话**不留半成品**(若该事务已归档 WAL 则按提交语义处理,见 SPEC-P3 FR-313/315);重启后客户端重连即可用;库与数据一致
- **验收方式**:重启前后对拍行数与值

### 场景 11 · 并发会话与事务隔离(回归)

- **给** `fed` 上的两个会话
- **当** 会话 A `BEGIN` 后改一行但未提交,会话 B 读同一行
- **那么** B 读到**旧值**(各自快照);A 提交后 B 的新语句看到新值;两会话抢同一行时后提交者拿到写写冲突(SPEC-P3 SC-202 语义在常驻进程下**不变**)
- **验收方式**:复用 `scripts/sql/26/27/28` 系列脚本,改为连同一个 `fed`

## 4. 功能需求

> 编号从 **FR-401** 起(SPEC-P3 用到 FR-370)。**FR 是验收的核对清单**,每条都必须可执行、可观测。

### 第零步 · 常驻 FE(FR-401 ~ FR-415)

| 编号 | 需求 |
|---|---|
| FR-401 | `fed` 是**常驻进程**:启动后一直运行,监听协议端口与心跳端口,直到收到停止信号 |
| FR-402 | `fed` 持有**唯一的 catalog 权威内存缓存**;所有会话共享同一份读视图,写路径加锁(一个进程内的强一致) |
| FR-403 | 每个客户端连接 = 一个会话。会话独立持有:**当前库**、**当前事务**、**写集**、语句级状态 |
| FR-404 | 同一会话内语句**串行**执行;不同会话**并发**执行 |
| FR-405 | 新连接建立后:若客户端指定了 database,则把它设为当前库;未指定则为 `default` |
| FR-406 | 会话断开时:若存在未提交事务,必须**回滚**(协议层断开、CLI `exit`、`fed` 优雅退出都适用) |
| FR-407 | BE 不可达时 `fed` 的启动行为沿用 P2:报明确原因(不静默起一个连不上 BE 的 `fed`) |
| FR-408 | CLI 通过协议连 `fed`(`--host` / `--port` / `--user` / `--password` / `--database`,或配置文件);**不再自带 FE**、不再直连 BE |
| FR-409 | 启动与停止脚本只保留两个:`scripts/start-be.sh`、`scripts/start-fe.sh`;**两者都支持 `--daemon`(后台启动,PID 与日志落 `tmp/`)与 `stop`(优雅停止,上限 5 秒后强制)**;不带 `--daemon` 即前台启动;`start-fe.sh cli` 起瘦客户端 CLI。Win 原生 `.cmd` / `.ps1` 版本本期不做(接口 I-10 的该部分顺延) |
| FR-410 | `SHOW SESSIONS` 输出:会话 id、连接源、当前库、是否在事务中、开始时间 |
| FR-411 | 会话上限 `session_max`(默认 64):超限拒绝连接并给明确错误 |
| FR-412 | 空闲超时 `session_idle_timeout`(秒,默认 0 = 不超时):超时关闭会话并回收 |
| FR-413 | `fed` 优雅退出:①停止接受新连接 → ②等在途语句结束(上限时间,超时断开)→ ③释放端口 → ④退出码 0 |
| FR-414 | CLI / `mysql` 客户端 / JDBC **可同时**连同一个 `fed`,看到同一份 catalog(场景 1) |
| FR-415 | 心跳端口由 `fed` 独占;`heartbeat_enabled = false` 时 `fed` 不监听心跳端口,但**协议端口与 SQL 功能照常**(并发验收仍要能用) |

### 第一步 · 多库命名空间(FR-416 ~ FR-430)

| 编号 | 需求 |
|---|---|
| FR-416 | `CREATE DATABASE <name>`:重名报错;名字规则与表名一致(支持反引号);名字做**大小写不敏感**处理(统一按小写存储,见 K69) |
| FR-417 | `DROP DATABASE <name>`:库**非空则拒绝**,提示"库非空,请先删表"(本期不级联);`default` 库不可删 |
| FR-418 | `USE <name>`:切换会话当前库,**只影响本会话**;库不存在报错(1049) |
| FR-419 | 限定名 `db.tbl` 在 `SELECT` / `INSERT` / `UPDATE` / `DELETE` / `CREATE TABLE` / `DROP TABLE` 里都可用 |
| FR-420 | 表名唯一性 = **库内唯一**;不同库可有同名表(场景 4) |
| FR-421 | 表 ID 仍**全局唯一**:由 `sys_counters.next_table_id` 统一分配,**不按库分段** |
| FR-422 | `SHOW DATABASES` 列出全部库(含 `default`) |
| FR-423 | 库元数据持久化到 `sys_databases`(系统表,见 §5.4) |
| FR-424 | `sys_tables` 增"所属库"列;**老数据目录宽容读**(缺列 = `default`),**key 布局不变、`format_version` 不变** |
| FR-425 | `next_table_id` 初值改为 **64**(仅新建库);老库保持现有值并继续递增 |
| FR-426 | FE 的表 ID 校验从"`ID ≥ 16` 即用户表"改为"**ID 不在系统表登记表内即用户表**"(设计方案 §4.4 落实项) |
| FR-427 | 未 `USE` 过任何库时,当前库 = `default`;`default` 库在首次启动时**幂等创建** |
| FR-428 | 库级 DDL 与 `USE` 都是**元数据/会话操作**,不走 BE 的 SQL 语义(库不落 key,BOSS:BE 完全不知道"库") |
| FR-429 | 一条 SQL 里引用**两个库**的表 → 明确报错不支持(本期不做跨库语句) |
| FR-430 | `SHOW TABLES` 只列**当前库**的表 |

### 第二步 · MySQL 协议(FR-431 ~ FR-455)

| 编号 | 需求 |
|---|---|
| FR-431 | `fed` 监听 `mysql_port`(默认见 §12 I10);端口被占用时启动失败并报明确原因 |
| FR-432 | 握手采用 **Protocol::HandshakeV10**:server version 串、connection id、`auth-plugin-data`(20 字节)、能力位、字符集、状态位、认证插件名 |
| FR-433 | 认证:`mysql_native_password`;密码错返回 **1045**(`ER_ACCESS_DENIED_ERROR`),错误信息不泄露库内细节 |
| FR-434 | 能力位集合:置 `CLIENT_PROTOCOL_41` / `CLIENT_PLUGIN_AUTH` / `CLIENT_SECURE_CONNECTION` / `CLIENT_CONNECT_WITH_DB` / `CLIENT_TRANSACTIONS`;**不置** `CLIENT_MULTI_STATEMENTS` / `CLIENT_SSL` / `CLIENT_DEPRECATE_EOF`(本期用 EOF 分帧,兼容性更好) |
| FR-435 | `COM_QUERY`:执行 SQL,返回文本结果集或 `OK` / `ERR` |
| FR-436 | `COM_INIT_DB`:等价于 `USE`,只影响本会话 |
| FR-437 | `COM_PING` 返回 `OK`(探活) |
| FR-438 | `COM_QUIT` 关闭会话(走 FR-406 的回滚逻辑) |
| FR-439 | 文本结果集:列数 → N 个列定义包 → `EOF` → 行(每个值长度编码字符串,`NULL` 用 `0xFB`)→ `EOF` |
| FR-440 | 错误码映射见 §5.2;错误信息**必须可读**(表名 / 列名 / 主键原样带上) |
| FR-441 | 事务:`BEGIN` / `COMMIT` / `ROLLBACK` 经 `COM_QUERY` 执行;会话处于事务中时,`OK` / `EOF` 包的状态位必须置 `SERVER_STATUS_IN_TRANS`;`autocommit` 视作已开(见 K65) |
| FR-442 | 连接期兼容语句白名单(见 §5.5):必须**接受并给出合理响应**,不得报错 |
| FR-443 | 结果集按 `utf8mb4` 编码发送(字符集 id 45) |
| FR-444 | 单包载荷超过 `16MB-1` 时按协议切片续发(大结果集的正确性,不必做流控) |
| FR-445 | `JSON` 列在协议层以**文本**(JSON 字符串)发送(存储仍是 Binary JSON,见 K68) |

## 5. 数据与格式

### 5.1 关键约束:BE 与 key 布局**零改动**


## 6. 外部评审必答项的正面回答

### 1. 为什么 FE 必须变成常驻进程,不能"CLI 里顺手跑一个协议监听"?

① **JDBC 连接池持长连接**:连接的生命周期由客户端决定,不可能对应"一个 CLI 进程的运行期";② **会话状态必须活在服务端**(当前库、事务、写集)—— 客户端断开重连要能拿到干净的会话;③ **协议端口要一直听着**,否则客户端连不上;④ `fed` 唯一持有 catalog 权威缓存,顺带关掉"跨进程 DDL 不可见"这个已登记缺口(它正是"每个 CLI 各持一份缓存"造成的)。⑤ P8 的 Web 控制台 / 监控 / 任务列表也需要一个常驻宿主,不用再另起进程。

### 2. 常驻之后,并发模型是什么?会不会把 P3 的事务语义搞坏?

`fed` 内:每会话一个执行线程(会话内语句串行,符合 SQL 会话语义),共享一份 catalog + 一个执行入口;写路径(DDL、事务提交)加锁串行,读路径走 MVCC 快照。**P3 的事务语义一条不改** —— 快照由 BE 的 `BeginTxn` 水位决定,冲突检测仍在 BE 提交时做;`fed` 只是把多个会话接到同一个执行入口上(场景 11 专门回归这一条)。

### 3. 为什么只提供 `mysql_native_password`,不做 `caching_sha2_password`?

`caching_sha2_password` 需要 RSA 公钥交换或 TLS 通道,而我们本期**明确不做 TLS** —— 在明文连接上实现它没有收益,只会引入密钥管理。`mysql_native_password` 是"挑战-响应",口令**不以明文过网**(尽管整个连接仍是明文)。代价:连接串里不用特意指定插件,但服务端要按该插件规则校验(见 K63)。

### 4. 为什么不宣布自己是 MySQL 8.0?

若 server version 报 8.0,客户端会期待 8.0 的默认认证插件、`utf8mb4_0900_ai_ci` 排序规则、以及更全的 `information_schema`。本期实现的是**可测子集**,因此 server version 串按 **5.7 系** 报告(见 K64)、字符集 45(`utf8mb4_general_ci`),把"我不是 8.0"说清楚,避免客户端走 8.0 专有分支。

### 5. 多库为什么不需要动 BE?

表 ID 全局唯一 → key 里没有任何"库"信息 → "这个表属于哪个库"是 FE 的元数据。BE 仍然只认"一段 key 范围"。**库本身不落 key**(不占表 ID、不占索引 ID),`CREATE DATABASE` 只是往 `sys_databases` 写一行。

### 6. 协议层会不会变成"第二套执行引擎"?

不会,FR-447 写死:协议层只做**分帧 + 编解码 + 命令分发**,语句一律交给同一个 Parser / Executor。协议层不得出现任何 SQL 语义判断。

### 7. 明文协议的安全边界怎么交代?

① 只面向受信网络(内网 / 本机),文档与验收报告都写明;**② 口令在连接里走挑战-响应,不明文过网**(但表数据是明文过的,这一点必须写清楚,不能让人误以为有加密);③ 若要上 TLS,必须另立决策(本期不做)。

## 7. 关键技术决策(本期默认值)

| 编号 | 决策 | 说明 |
|---|---|---|
| **K60** | `fed` 的并发模型:每会话一个执行线程 + 共享 catalog + 写路径加锁 | 会话内串行符合 SQL 语义;不引线程池框架,用 JDK 自带并发原语(依赖红线) |

## 9. 边界与异常清单

| # | 情形 | 期望行为 |
|---|---|---|
| 1 | `CREATE DATABASE` 用保留名(`default` / `sys_*`) | 拒绝,错误可读 |
| 2 | 库名超长 / 空 / 含非法字符 | 拒绝(限长 64,与表名规则一致) |
| 3 | `USE` 一个已删除的库(会话里留着旧名) | 报"库不存在",当前库不变(不静默切到 default) |
| 4 | 会话 A 正在用库 X,会话 B `DROP DATABASE X` | 按 FR-417:库非空则拒绝;若为空,允许删;A 的当前库变为"不存在",下一条带库语义的语句报 1049 |
| 5 | 老数据目录里 `sys_tables` 有 `db` 列但值为空 | 视为 `default`(宽容读) |
| 6 | `next_table_id` 老值 < 64 | 不强行改写;新建表继续按老值分配(老库保持连续),但**不得分配进登记表占用的 ID**(校验见 FR-426) |
| 7 | 客户端在握手中途断开 | 不记录为登录失败刷屏;释放连接资源 |
| 8 | 客户端发送超长单包(> 16MB) | 按协议切片读;超过 `max_allowed_packet` 上限则报错断开 |
| 9 | 客户端发送非法能力位组合(如置了 `CLIENT_SSL`) | 按不支持的参数处理:返回错误并断开(不静默降级) |
| 10 | 结果集行数极大 | 逐批发送,不整体驻留内存(至少要按行流式写出) |
| 11 | 语句执行中途客户端断开 | 事务回滚;无事务语句按已提交处理(与 CLI 行为一致) |
| 12 | `fed` 启动时端口被占(协议口或心跳口) | 启动失败 + 明确原因(沿用 P2 的心跳端口行为) |
| 13 | `fed` 运行中 BE 挂掉 | 在途语句报 BE 不可达;`fed` 不退出;BE 恢复后新语句可用(沿用 P2 存活判定口径) |
| 14 | 同一会话内并发语句(客户端不等响应就发下一条) | 按协议顺序串行处理(不并发执行同一会话的语句) |
| 15 | `information_schema` 查询(未实现时) | 不得报错导致客户端连不上;按 I9 拍板口径处理 |
| 16 | CLI 与 `fed` 版本不一致(协议子集变化) | 握手时带上版本串;不兼容时给"版本不匹配"的明确提示 |
| 17 | 库名大小写混写(`USE SHOP` / `shop`) | 按 K69 视为同一个库 |
| 18 | `DROP TABLE` 后 `SHOW TABLES` | 不再列出;表 ID 不复用(沿用 P2 口径) |
