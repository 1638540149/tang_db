## 1. 为什么现在做(基线)

P1~P6.1 已经把「存储 + SQL + 事务 + 索引 + 列存/向量化 + CBO + 执行层性能」这套地基跑通,当前实测基线(同机:i7-13620H / 40GB / Go 1.27 / Java 17.0.12):

| 场景 | 现状(P6.1 验收) |
|---|---|
| 批量导入(3 列无二级索引) | 15,581 / 17,844 行/秒 |
| 全表扫描 + 聚合(5 万行) | 1,020,408 行/秒 |
| 三表 JOIN(128k ⋈ 50k ⋈ 20k) | 166ms |
| 单行 INSERT P99 | 11.33ms |
| 硬件加速 | 无 GPU、无第三方向量库(**依赖红线**:BE 只允许 grpc + protobuf) |

P7 要回答的问题不是「能不能再快」,而是:**在没有 hnswlib / faiss 的前提下,自研一套随 LSM 演进的向量索引,并让优化器在「结构化过滤 + 向量相似」之间选对路径。** 这是项目三个创新点里的第二个和第三个。

## 2. 范围

### 2.1 本期做(六组)

**A 组 · 类型与语法(FR-731 ~ FR-741)**

- 新增列类型 `VECTOR(n)`:定长 float32 向量,`n` 为维度(1~4,096)。
- 新增向量字面量:`'[0.12,0.34,…]'`(字符串形式,FE 解析成 float32,长度必须等于列维度)。
- 新增距离函数:`l2_distance(v1,v2)`、`cosine_distance(v1,v2)`、`inner_product(v1,v2)`。
- 建向量索引:`CREATE VECTOR INDEX <名> ON <表>(<向量列>) WITH (metric='l2', m=16, ef_construction=200)`;`DROP INDEX` 同样适用。
- `DESC` / `SHOW INDEX` / `SHOW CREATE TABLE` 能看出「这是向量索引」以及度量/维度/图参数。
- `information_schema` 新增 `VECTOR_INDEXES` 视图(基于系统表 9,见 §5)。

**B 组 · 图段存储(FR-742 ~ FR-752)**

- 每个 segment 至多一个图段文件 `<segNum>.hnsw`,与 segment **同生命周期**:segment 落盘后后台构建、图写完 fsync 后才在 MANIFEST 里可见、segment 被 compaction 回收时图一起删。
- 图段格式按设计文档 §13.4:元信息(维度/度量/层数/入口点/M/efConstruction/节点数)→ 第 0 层邻接 → 第 1 层 → … ;向量数据**引用** segment 里的向量列,不重复存(除非该列后续被投影掉,见边界 132)。
- MANIFEST 增字段记录「segment → 图文件 + 图参数 + 构建水位」;`format_version` 由 2 升 **3**,老目录按 P3 的既定策略**拒绝启动**(不静默兼容、不自动迁移)。
- 崩溃恢复:加载时校验图段与 segment 的节点数/校验和;对不上 → 标记待重建,后台补建,**不影响查询正确性**(该 segment 退化为暴力扫描)。
- compaction 后必须重建受影响分段的图(旧图随旧 segment 删除)。

**C 组 · 检索执行(FR-753 ~ FR-763)**

- `ORDER BY l2_distance(col, '<字面量>') LIMIT k` 触发向量检索:**每段各出 top-k,再归并**,memtable 部分走暴力计算(不建图)。
- 多段并发检索(复用 P6.1 的并行框架),归并按距离稳定排序(距离相同按主键升序,保证结果可复现)。
- MVCC 过滤:检索出的候选按快照可见性过滤(已删/被覆盖的丢弃);过滤后不足 K 条时按**可迭代候选扩展**(`ef` 翻倍,直到够 K 或达 `ef_max`)。
- 停止条件三类写死:数量条件、预算条件、质量条件(召回目标),**不允许把"凑够 K 条"当成"Top-K 正确"**。
- 预算用尽仍不足 K 条:小数据量回退**精确暴力**(阈值可配),否则返回不足 K 条并标 `partial=true`。
- 结果自描述:`approximate` / `ef_used` / `candidates_examined` / `partial` 四个字段,`EXPLAIN` 与协议结果都能看到。
- 精确模式:`EXPLAIN`/会话开关可强制 `exact`(全暴力),用于对拍与召回率测试。
- 小表/低候选:行数低于阈值(默认 1 万)或过滤后候选低于阈值 → 直接暴力,不建图不选路。

**D 组 · 混合查询选路(FR-764 ~ FR-771)**

- 同一条查询既有结构化谓词又有向量 `ORDER BY ... LIMIT`:`EXPLAIN` 必须给出**选了哪条路径**及依据(选择率估算值/候选量)。
- 路径 A「先过滤后检索」:把结构化条件的结果作为**允许集**(主键列表或布隆)下推给检索算子,图遍历只在允许集内展开候选。
- 路径 B「先检索后过滤」:先取近似候选再按谓词过滤,候选扩展量走 C 组的可迭代逻辑,**不写死倍数**。
- 决策依赖 P6 的统计信息;**统计过期/缺失时不赌**:一律退化为路径 B(只依赖候选量,不依赖选择率估得准不准)。
- 两条路径结果集必须**逐行一致**(顺序也一致),只是快慢不同——这是 ★ 场景。

**E 组 · 推理下推(FR-772 ~ FR-782)**

- `ai_embed(<文本表达式>)` 作为**算子**参与 `INSERT ... SELECT`:按批(默认 1,024 行)调用外部模型端点,批量推理,结果作为向量列写入。
- 端点配置(`ai_endpoint` / `ai_model` / `ai_dim` / `ai_timeout_ms` / `ai_batch_rows` / `ai_cache_entries`),不进库、不存权重。
- **幂等**:幂等键 = `hash(模型版本 + 向量维度 + 规范化文本)`,同键永不重复调用;BE 内存 LRU 缓存,命中率可观测。
- **失败语义**:超时指数退避 + 重试上限 + 连续失败熔断;批量失败可拆小重试;整批失败则该批**不进写路径**(一个字都不写)。
- **校验**:维度不符 / 非法数值 / 模型版本与配置不一致 → 直接失败,绝不写半成品向量。
- **副作用边界**:同一行的向量与其它列值在同一条 WAL 批记录里,不拆开;但不承诺跨行原子性(那是事务的事)。
- `ai_embed` **不允许**出现在 `WHERE` 谓词、`GROUP BY`、`ORDER BY`(会诱导逐行调用与不可预测的副作用),只允许在 SELECT 投影与 INSERT ... SELECT 中。

**F 组 · 门限与可观测,以及 P6.1 挂账(FR-783 ~ FR-790)**

- 本期认领 P6.1 的三条遗留(见 §10):`SHOW INDEX FROM <表> FROM <库>` 双 FROM 兼容、扫描层并行阈值 `parallel_min_rows`、FR-715/716 量化取证。
- `SHOW VECTOR INDEXES`(或 `information_schema.VECTOR_INDEXES`)输出:表/列/维度/度量/段数/节点数/构建状态/待重建段数。
- `EXPLAIN` 增「向量检索」行:路径(A/B)、近似/精确、`ef`、候选量、允许集来源。
- 门限(见 §7 SC):召回率 ≥ 95%(矩阵口径)、10 万行×128 维 top-10 ≤ 100ms、混合查询两条路径结果逐行一致。

### 2.2 本期明确不做(逐条写死归属,避免被当成 bug 报回来)

| 不做项 | 归属 |
|---|---|
| 全文/关键词检索(倒排索引、BM25 打分) | **P10**(单独一期,不塞进 P7) |
| 多模态原文件存储(`TEXT`/`BLOB` 大对象、图片/音频解码) | **P11** |
| 地理空间类型与空间索引 | **P12** |
| 稀疏向量 / 多向量列联合检索 / 向量量化压缩(float16 可选项除外) | 未排期,记为候选 |
| 向量列做**主键**或**二级索引**(普通 B 树) | **不做**,报 1235(与 `JSON` 同口径) |
| `ai_embed` 出现在 `WHERE` / `GROUP BY` / `ORDER BY` | **不做**,报 1235 |
| text2sql、语义标签、UDF 市场 | **P8** |
| 自适应优化(运行时反馈改计划)、智能索引、根因诊断 | **P14** |
| GPU 加速 / 第三方向量库(hnswlib、faiss、ScaNN 等) | **永不做**(依赖红线) |
| 分布式多副本 / 向量索引跨节点拆分 | 当前单机架构,不排期 |
| 窗口函数、CTE(`WITH`)、视图、`ALTER TABLE` | 仍未排期(P8 之后候选) |
| 结果集**跨事务**流式一致性(游标跨提交) | 不做;P7 的流式只保证单语句内 |

## 3. BDD 场景(四跳:场景 → FR → SC → 脚本断言)

### 场景 1(常规):一条 SQL 完成向量化入库
- **给**:库里有 `docs(id INT PRIMARY KEY, title VARCHAR(200), content VARCHAR(2000), embedding VECTOR(128))`,已配好模型端点
- **当**:`INSERT INTO docs SELECT id, title, content, ai_embed(content) FROM raw_docs`
- **那么**:`SELECT COUNT(*) FROM docs` 行数与 `raw_docs` 一致;`embedding` 非 NULL 且维度为 128;模型被调用的次数 ≤ ⌈行数/1024⌉(不是每行一次)
- **反例**:端点不可用 → 整条语句失败,`docs` 行数**不变**(一个字都没写)
- **验收方式**:FR-772/773/776,SC-425/426

### 场景 2(常规):向量检索 + 结构化过滤
- **给**:`docs` 10 万行,`embedding` 已建向量索引
- **当**:`SELECT id,title FROM docs WHERE category='健康' ORDER BY l2_distance(embedding,'[…]') LIMIT 10`
- **那么**:返回 10 行且全部满足 `category='健康'`;结果与 `exact` 模式对拍召回 ≥ 95%;`EXPLAIN` 显示路径与 `ef`
- **反例**:结构化条件命中 0 行 → 返回 0 行(不是报错,也不能退化成全表 top-10)
- **验收方式**:FR-764~768,SC-421/422

### 场景 3(★ 并发):写入与检索并发
- **给**:持续 `INSERT`(每批 500 行,带向量)同时跑 8 个检索会话
- **当**:查询与写入交错运行 60 秒
- **那么**:每次检索都基于同一快照(不出现"同一查询两次返回不同结果");不出现 panic/deadlock;检索延迟 P99 不超过空载的 2 倍
- **验收方式**:FR-756/757,SC-427

### 场景 4(★ 崩溃):图段构建中途强杀
- **给**:刚灌入 5 万行,后台正在构建图段
- **当**:构建到一半强杀 BE,重启
- **那么**:重启后服务可用;该 segment 或"旧图+新数据"或"标记待重建并退化为暴力",**查询结果与强杀前一致**;后台补建完成后 `SHOW VECTOR INDEXES` 的待重建段数归零
- **反例**:强杀发生在"图写了一半、MANIFEST 还没记"时 → 图文件必须被丢弃(不能当有效图加载)
- **验收方式**:FR-746/747,SC-428

### 场景 5(回归):精确/近似两条路结果一致
- **给**:同一批数据
- **当**:同一查询分别用 `exact` 与 ANN 各跑一次
- **那么**:`exact` 结果可复现(同距离按主键升序);ANN 的 Recall@10 ≥ 95%,且 `approximate=true`
- **验收方式**:FR-759/760,SC-421

### C 组 · 检索执行

| 编号 | 需求 |
|---|---|

| FR-761 | 结果自描述字段:`approximate` / `ef_used` / `candidates_examined` / `partial`,CLI 与 MySQL 协议结果都要能带出(新增列或注释形式,见 K164) |
| FR-762 | 小表/低候选直接暴力:表行数 < `vector_bruteforce_rows`(默认 1 万)或允许集候选 < 该阈值 → 不建图不选路 |
| FR-763 | `JSON` 列、`VECTOR` 列不允许出现在 `GROUP BY`/`DISTINCT`/`ORDER BY`(除向量距离函数)/普通比较中,一律 1235 |

### D 组 · 混合查询选路

| 编号 | 需求 |
|---|---|
| FR-764 | 同一条语句含结构化谓词 + 向量 `ORDER BY ... LIMIT`:优化器必须选一条路径并在 `EXPLAIN` 说明依据 |
| FR-765 | 路径 A(先过滤后检索):结构化谓词结果作为**允许集**(主键集合或布隆)下推,图遍历只在允许集内展开;`EXPLAIN` 标 `allow-list` |
| FR-766 | 路径 B(先检索后过滤):先取候选再按谓词过滤,候选扩展走 FR-758 的可迭代逻辑,不写死倍数 |

| FR-771 | `EXPLAIN` 对混合查询输出:结构化选择率估算、选用路径、允许集大小、候选量、是否近似 |

### E 组 · 推理下推

| 编号 | 需求 |

## 5. 数据与格式

### 5.1 向量列在行内的编码

沿用 P5 的行值格式 `[版本1][表ID4][列数2][nullmap][len][bytes]×n`,向量列占一个「定长槽」:

```
向量列槽 = 4×n 字节,小端 float32 逐个排列;精度 float32(不做有损量化)
```

- FE 侧 `ProjectedCodec` 增 slot kind `VECTOR_FIXED`(宽度 = 4n),BE 侧仍只按偏移切片、**不需要知道这是向量**(与 P6.1 的红线一致)。
- 距离计算分两处:**查询执行在 FE 侧算**(BE 只按行序批量取向量);**图段构建与图内距离在 BE 内部算**(BE 拥有数据目录,FE 不得写 BE 文件),BE 只认 FE 下发的「定长 float32 槽 + 维度 + 度量操作码」。取舍见 K161。

### 5.2 图段文件格式(`<segNum>.hnsw`)

```
┌────────────┬──────────────────────────────────────────────┐
│ 魔数 8B     │ "TDHNSW\0\0"                                 │
│ 版本 u32    │ 1                                            │
│ dim u32     │ 向量维度                                     │
│ metric u8   │ 0=L2 1=Cosine 2=InnerProduct                 │
│ levelCount u32 │ 层数                                      │
│ entryPoint u64 │ 入口节点(0 层行序号)                      │
│ m u32 / efConstruction u32 │ 建图参数                        │
│ nodeCount u64 │ 节点数 = 该 segment 里可见的向量行数        │
│ buildSeq u64  │ 构建时 segment 的序号(用于与 MANIFEST 对齐) │
│ 节点表      │ nodeCount × (rowOrdinal u64)                 │
│ 第 L 层…    │ 每层:邻接表(定长 m 槽 + 变长溢出段)        │
│ 校验和 8B   │ CRC64(以上全部字节)                        │
└────────────┴──────────────────────────────────────────────┘
```

- **向量数据不存图里**:检索时用 `rowOrdinal` 回到 segment 的列数据取向量(避免双份存储与不一致)。
- 图的层数与每个节点的层高由 `m` / `efConstruction` 决定(标准 HNSW 掷骰子策略,种子固定 → 同一份数据重建结果可复现)。

### 5.3 MANIFEST 增量与系统表

```json
"vec_indexes": [
  {"index_id": 7, "table_id": 128, "segment": 42, "file": "42.hnsw",
   "dim": 128, "metric": 0, "m": 16, "ef_construction": 200,
   "node_count": 51200, "state": "READY", "build_seq": 42}
]
```

- `format_version` 2 → 3;老目录拒绝启动(P3 K54 同口径)。
- 系统表 **9** `sys_vec_indexes`(元数据权威副本,列):`table_id` / `index_id` / `column_ordinal` / `dim` / `metric` / `m` / `ef_construction` / `state` / `created_at`。段级状态在 MANIFEST,不在系统表(避免双写)。
- 索引 ID 复用 P4 的每表计数器 `next_index_id:<table_id>`(普通索引与向量索引同一命名空间)。

### 5.4 新增配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `vector_metric` | `l2` | 建索引默认度量(可被 WITH 覆盖) |
| `vector_m` / `vector_ef_construction` | 16 / 200 | 建图默认参数 |
| `vector_ef_search` | 64 | 检索默认 `ef` |
| `vector_ef_max` | 512 | 可迭代扩展上限 |
| `vector_bruteforce_rows` | 10000 | 低于此行数直接暴力 |
| `exact_fallback_rows` | 10000 | 预算用尽时回退精确的上限 |
| `allow_list_max_ratio` | 0.3 | 允许集超过表行数该比例则不走路径 A |
| `parallel_min_rows` | 50000 | **FR-784**:扫描层并行阈值 |
| `ai_endpoint` / `ai_model` / `ai_dim` | 空 / 空 / 0 | 推理端点;缺失时用 `ai_embed` 报错 |
| `ai_batch_rows` / `ai_timeout_ms` / `ai_cache_entries` | 1024 / 5000 / 10000 | 批量、超时、缓存 |
| `ai_max_retries` / `ai_breaker_batches` | 3 / 5 | 重试与熔断 |

非法值一律**启动失败并指出第几行**(与 P6.1 的 9 项同口径)。

## 6. 关键技术决策(K 表)

> 编号续排:上期最大 K156,本期从 **K157** 起。每行「决策点 | 推荐值 | 理由」;想换就一句话。

| 编号 | 决策点 | 推荐值 | 理由 |
|---|---|---|---|
| K157 | 向量精度 | **float32,不做有损量化** | 量化会改变距离关系、直接影响召回;float16 作为后续可选 |
| K158 | 维度上界 | 1~4,096,超限 1235 | 4,096×4B = 16KB/行,再大行会爆;向量场景 128~1,536 足够 |
| K159 | 建图默认参数 | m=16 / ef_construction=200 / ef_search=64 | HNSW 论文常用默认值,10 万级数据召回与构建时间平衡 |
| K160 | 图段数量 | **一 segment 一图段**(不合并跨段图) | 与 LSM 生命周期天然对齐,compaction 只重建受影响段;合并成大图会让"写入即重建全图" |
| K161 | 距离计算位置(分两处) | **查询执行:FE 算距离,BE 只按行序批量取向量;图段构建与图内距离:BE 内部算** | BE 拥有数据目录、必须自己写 `<seg>.hnsw`(INV-16:FE 不得写 BE 目录),所以建图只能在 BE 做;但它只需要 FE 下发的「定长 float32 槽 + 维度 + 度量操作码」,不需要知道列名/类型名 —— 与红线不冲突。检索侧仍走 FE,避免把"哪列是向量"泄漏给 BE |
| K162 | 是否改磁盘格式 | **改**(format_version 2→3) | 图段必须与 segment 绑定,MANIFEST 不记就没有原子发布;老目录拒绝启动,与 P3 一致 |
| K163 | 新数据(memtable) | **不建图,暴力** | 量小,暴力更快更准,零召回损失;避免内存里维护可变图 |
| K164 | 结果自描述字段的对外形态 | **CLI 输出多一行注释;MySQL 协议作为额外结果列(仅当语句带 `WITH VECTOR INFO`)** | 不污染普通查询的列集合,又能在需要时看到 `ef_used`/`candidates_examined` |
| K165 | 召回验收口径 | **以暴力精确为基准,四维矩阵,Recall@10 ≥ 95%** | 单一数据集自测会掩盖召回退化;矩阵能覆盖删除/更新/段数/选择率 |
| K166 | 预算用尽行为 | **按 `exact_fallback_rows` 回退暴力;超阈值才返回 partial** | 宁可多算一点,也不许把近似包装成完整 Top-K |
| K167 | 混合查询选路阈值 | 选择率 **≤ 0.1 走路径 A**,0.1~0.3 比代价,> 0.3 走路径 B;统计 stale 一律 B | 路径 A 的前提是过滤真能砍掉一个数量级;阈值写死避免"玄学调参" |
| K168 | 允许集表达 | **主键集合(≤ 1 万)优先,超了退化为布隆** | 布隆有假阳性(会多算距离但不会漏行),主键集合精确但占内存 |
| K169 | 推理调用位置 | **FE 侧算子(EmbedOp),不进 BE** | 外部 HTTP + 重试策略属于执行编排,FE 已有并行框架;BE 只收"已经是向量"的字节 |
| K170 | 推理幂等键 | `hash(模型版本+维度+规范化文本)` | 换模型就换键,避免复用旧模型的向量 |
| K171 | 推理失败时已写行 | **回滚到语句前**(单语句事务) | 与现有 DML 语义一致;不引入"部分成功"的新语义 |
| K172 | 向量列能否做主键/普通索引 | **不能,报 1235** | 定长浮点无法给出严格保序编码(K16 红线) |
| K173 | `ai_embed` 出现在谓词 | **禁止,报 1235** | 会诱导逐行调用外部服务,且结果不可预测、无法预估代价 |
| K174 | 图段构建时机 | **segment 落盘后后台异步 + 可显式 REBUILD** | 前台写入不受建图拖累;显式重建用于参数变更 |
| K175 | 小数据量阈值 | 表行数 < 1 万直接暴力 | 建图收益为零,暴力零召回损失 |
| K176 | 检索并发度 | 取 `query_parallelism`,但**段数 < 2 不并发** | 复用 P6.1 框架,避免小数据量的线程开销 |
| K177 | 图段与向量列的耦合 | 图只存行序号,**向量从 segment 读** | 避免双份存储导致的不一致与空间浪费 |
