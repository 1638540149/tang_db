## 1. 为什么现在做(实测依据)

同机同数据(Windows 11 / i7-13620H / 40GB / Go 1.27 / Java 17.0.12)实测:

| 场景 | 现状 | 参照系 |
|---|---|---|
| 批量导入(1 列无索引) | ≈ 1,100 行/秒 | PostgreSQL `COPY` 5~10 万行/秒 |
| 批量导入(9 列 + 2 索引) | ≈ 320 行/秒 | 同上 |
| ecom orders 导入(9 列 2 索引) | 50,000 行 / 64 秒 ≈ 780 行/秒 | 同上 |
| 全表扫描 + 聚合 | ≈ 9 万行/秒(ecom 四表 26.8 万行约 3 秒) | Doris/ClickHouse 数十万~百万行/秒 |
| 三表 JOIN(128k ⋈ 50k ⋈ 20k) | ≈ 10 秒 | 同类引擎 几十毫秒~亚秒 |
| 单行 INSERT P99(P3.5 基线) | 11.50 ms | — |

根因(读码定位,五处):

| # | 位置 | 问题 |
|---|---|---|
| 1 | `be/internal/store/engine.go:395-405` + `mvcc.go:98` | 写集里**每个 key** 各建一次 scanner 做版本查询 |
| 2 | `be/internal/memtable/memtable.go:118-127` | `MemTable.Iterator()` 把整张跳表**拷成切片**;于是单批成本 = 批行数 × memtable 条目数 |
| 3 | `be/internal/store/engine.go:387` | 上述全过程在 `commitMu` 内串行,**每批一次 fsync** |
| 4 | `proto/tangdb.proto:ScanRequest` / `TangDbClient.java:53` | 扫描**无列投影、无谓词下推**(整行回传)、期限写死 5 秒 |
| 5 | `fe/.../query/QueryEngine.java` | 所有算子(JOIN/聚合/排序)**FE 单线程、逐行 Java 对象**,无并行、无流式结果 |

结论:慢的两个数量级里,**BE 写入复杂度**与**FE 单线程执行 + 无下推**各占一半,必须一起动,单改一边拿不到量级收益。

## 2. 范围:四组(写路径 / 读路径 / FE 执行 / 协议与门限)

### 2.1 本期做

**A 组 · BE 写路径(FR-693 ~ FR-700)**

- 冲突检测改**单次区间扫描**(写集先按用户键排序去重,一次 scanner 走完 `[minKey,maxKey]` 并归并),禁止每 key 建 scanner。
- `MemTable.Iterator()` 改**惰性游标**(跳表下降 `Seek`,不分配整表切片)+ 写计数水位校验(超水位报 `unsafe` 由上层重建),另留 `IteratorSnapshot()` 给长生命周期调用方。
- **Group commit**:多个提交的 WAL 记录顺序追加后**合并一次 fsync**;每个事务必须在"覆盖它的 fsync"完成后才拿回 OK(这是正确性红线,不是性能选项)。
- WAL 追加走**复用缓冲池**,消除每批的大块分配;`commitMu` 只保护"排序→取号→追加",fsync 与 memtable 应用允许分组并行。
- 门限:内存缓冲与批量提交参数可配(`wal_buffer_bytes` / `group_commit_max_batch` / `group_commit_max_wait_ms`)。

**B 组 · BE 读路径(FR-701 ~ FR-710)**

- **列投影**:`ScanRequest` 增加**列槽表**(每列的序号与字节区间描述);BE 按"行框架协议"只拷贝被选中的列字节,其余丢弃。行框架 = `[nullmap][len][bytes]×n`,由 FE 下发 `nullmap_bytes` 与列数,BE 只按框架切片 —— **不理解列名/类型/语义**。
- **谓词下推**:FE 把单表谓词编译成**字节码**(`EQ/NE/LT/LE/GT/GE/IS_NULL/BETWEEN/IN/AND/OR/NOT`),参数是"列槽号 + 保序编码后的字面量字节";BE 用**字节比较**执行,不需要任何类型知识。整型/浮点/字符串/日期都靠保序编码统一为字节序。
- **分片扫描**:一次全表扫描按 key 范围切成 N 片(`ScanRequest` 现有 `start_key/end_key` 即可表达,不新增分片字段),FE 侧并发拉取。
- **段级剪枝加强**:ZoneMap/布隆在**列投影 + 谓词下推**后按列判定,减少无谓 chunk 解码;命中率写入 `SHOW SEGMENTS`。
- **零拷贝/少拷贝**:`RowBatch` 支持"原始字节块 + 偏移数组"返回(避免每条 KV 一次拷贝),并按 `batch_rows` 自适应(默认 4096,可配)。
- 顺序扫描**预读**:按 chunk 顺序预取下一个 segment 的 chunk(仅读,不改格式)。

**C 组 · FE 执行(FR-711 ~ FR-719)**

- **扫描并行 fan-out**:一次全表扫描按分片并发(线程池 `query_parallelism`,默认 min(8, CPU)),结果按分片有序归并,保证 ORDER BY 前的行集合与单线程一致。
- **算子并行**:Hash Join 的 build 按哈希桶分段并行、probe 并行;聚合按分组键分桶并行后二次合并;排序在分片内并行排序再归并(复用 P5 `Sorter`)。
- **流式结果集**:查询结果按 batch 直接写协议 socket(不再整表物化),`LIMIT` 命中即提前终止上游。
- **解码复用**:`RowCodec` 解码复用缓冲与基本类型数组(避免每行 `Object[]` 装箱),谓词求值在列式 batch 上做。
- **批大小自适应**:按行宽与选择率在 1024~8192 间调整。
- 并行与下推都必须能被开关整体关闭(`query_parallelism=1` + `pushdown_enabled=false` = 等价于 P6 行为)。

**D 组 · 协议、期限与配置(FR-720 ~ FR-725)**

- `proto` 变更(**仅加字段,不改语义**,proto3 向后兼容):`ScanRequest` 增 `column_mask` / `column_slots` / `row_frame` / `predicate`;`RowBatch` 增 `columnar_block`(可空,空则回退逐 KV)。改完必须 `scripts/gen-proto.sh` 重生成两侧桩代码。
- 期限三档可配:`rpc_deadline_seconds=5` / `rpc_bulk_deadline_seconds=60` / `rpc_scan_deadline_seconds=60`;批量导入、索引回填、`ANALYZE`、分片扫描走对应档。
- 新增配置:`query_parallelism` / `pushdown_enabled` / `wal_buffer_bytes` / `group_commit_max_batch` / `group_commit_max_wait_ms` / `scan_batch_rows`;写错即启动失败并指出行号。

**E 组 · 一致性与等价性验证(FR-726 ~ FR-730)**

- **结果等价**:`pushdown_enabled=false` + `query_parallelism=1` 时,与 P6 行为逐行一致(全量 SQL 回归对拍)。
- **数据一致**:group commit 下"返回 OK ⇒ 已 fsync";强杀后已提交数据零丢失(崩溃矩阵扩到 group commit 场景)。
- **冲突不漏检**:并发写者与批量导入混跑时,不得出现静默覆盖;冲突仍 100% 返回 1213。
- **谓词等价**:下推字节码与 FE 侧求值结果逐行一致,覆盖 NULL 三值、边界值、类型混合、空串/超长串。
- 所有门限带机器条件模板,不达标要写原因,不许改门限。

### 2.2 本期明确不做(均为非性能项,不是"推向 P8 的性能债")

| 不做 | 归属 / 理由 |
|---|---|
| 分布式 / 多节点 / 分片路由 | 设计文档 §5.4 明确先不分布式 |
| `VECTOR` 类型、HNSW、推理下推 | **P7** |
| 自适应优化(运行时反馈改计划)、智能索引、根因诊断 | **P14** |
| 表达式/函数/路径索引 | **P11 之后** |
| 窗口函数、`GROUPING SETS`/`ROLLUP`/`CUBE` | **P14 之后的候选** |
| `EXPLAIN ANALYZE`、慢查询日志、监控指标、备份恢复、Web 控制台、`mysql`/JDBC 兼容补齐 | **P8**(功能项,不是性能项) |
| 物化视图 / 结果缓存 / 查询缓存 | 未排期;`LIMIT` 提前终止已覆盖主要收益 |
| 跨行/跨段压缩编码改造(可查询编码) | 不做:与"BE 不懂列语义"冲突;本期用列投影 + 谓词下推拿等效收益 |

### 2.3 兼容性边界(补丁规约必带)

- **`proto` 加字段**:proto3 增量字段向后兼容,但需重生成桩代码;**两侧必须同版本部署**(单机项目,不做跨版本灰度)。
- **磁盘格式不变**:WAL 记录布局、segment/chunk、MANIFEST、系统表全部不变 → **不需要数据迁移**,老目录直接可用。
- **行框架协议**:`[nullmap][len][bytes]×n` 由 FE 下发参数,BE 只按字节偏移切片;`proto` 内不得出现表名/列名/SQL/类型名(只允许列序号、偏移、操作码、字节字面量)。
- **语义不变**:事务语义、错误码、SQL 行为、`EXPLAIN` 既有行、`SHOW` 家族一律不变。

### 2.4 保证 / 不保证

- **保证**:①结果逐行一致(开关可回退);②"返回 OK ⇒ 已 fsync";③崩溃零丢失;④冲突不漏检;⑤`proto` 无表列语义。
- **不保证**:线性加速(10 核机器按 3~6 倍估);慢盘上的 fsync 抖动;超大排序溢写仍受磁盘限制。

## 4. 需求(FR)

## 5. 数据与格式

### 5.1 `proto` 增量(仅加字段)

```
message ScanRequest {
  ... 既有 1~5 ...
  uint32 column_mask      = 6;   // 位图:第 k 位 = 是否要第 k 列
  bytes  column_slots     = 7;   // 每列槽位(序号+偏移描述),FE 生成
  bytes  row_frame        = 8;   // nullmap 字节数 + 列数(行框架参数)
  bytes  predicate        = 9;   // 字节码(FE 编译,BE 按字节比较执行)
  bool   columnar_result  = 10;  // 是否要列式块返回
}
message RowBatch {
  ... 既有 ...
  bytes columnar_block = 4;      // 原始字节 + 偏移数组;空则回退逐 KV
}
```

> 关键约束:以上字段里**没有**表名、列名、SQL、类型名;BE 只按"序号 / 偏移 / 操作码 / 字节"工作。

### 5.2 新增配置

| 配置 | 位置 | 默认 | 含义 |
|---|---|---|---|
| `query_parallelism` | `fe.conf` | `min(8, CPU)` | 扫描与算子的并行度 |
| `pushdown_enabled` | `fe.conf` | `true` | 列投影 + 谓词下推总开关 |
| `scan_batch_rows` | `fe.conf` | `4096` | 扫描批行数(自适应上限 8192) |
| `rpc_deadline_seconds` | `fe.conf` | `5` | 普通读写/事务 |
| `rpc_bulk_deadline_seconds` | `fe.conf` | `60` | 批量导入 / 索引回填 / ANALYZE |
| `rpc_scan_deadline_seconds` | `fe.conf` | `60` | 范围扫描 / 分片扫描 |
| `wal_buffer_bytes` | `be.conf` | `1MB` | WAL 追加缓冲池大小 |
| `group_commit_max_batch` | `be.conf` | `64` | 一次 fsync 最多合并的提交数 |
| `group_commit_max_wait_ms` | `be.conf` | `5` | 攒批最长等待(超时立即 fsync) |

## 6. K 决策表

| # | 决策点 | 推荐值 | 理由 |
|---|---|---|---|
| K144 | 下推的抽象层级 | **零语义原语**(列槽 + 字节比较字节码) | 拿到列投影与谓词下推的全部收益,同时不破"BE 不懂表列"铁律 |
| K145 | 行框架谁来定义 | FE 下发参数(`nullmap_bytes` + 列数),BE 只按 `[nullmap][len][bytes]×n` 切片 | 框架是编码约定不是语义;BE 仍不知道第几列叫什么、什么类型 |
| K146 | 谓词字节码 vs 表达式树 | **字节码**(栈式,10 余个操作码) | 比序列化表达式树小、解析快;BE 侧实现百行级 |
| K147 | 分片方式 | 用现有 `start_key/end_key` 切 key 范围,**不新增分片字段** | proto 改动最小;分片边界由 FE 按统计/段边界计算 |
| K148 | 并行模型 | FE 侧线程池 + 分片并发;BE 保持无状态单请求 | 不动 BE 并发模型,崩溃语义不变 |
| K149 | Group commit 上限 | 批 64 / 等 5ms | 单机 OLTP 常见取值;越大吞吐越高但尾延迟越差,5ms 足够摊平 fsync |
| K150 | Group commit 正确性实现 | fsync 世代计数,事务记住世代号 | 唯一能同时保证"合批省 fsync"与"返回 OK ⇒ 已落盘"的实现 |
| K151 | 惰性游标的并发安全 | 写计数水位 + `unsafe` 显式错误 | 宁可能重试,不许静默脏读 |
| K152 | 列式返回格式 | 原始字节块 + 偏移数组 | 避免每行一次 gRPC 消息与小对象;可复用缓冲 |
| K153 | 开关默认值 | 并行与下推默认**开**,对拍时关闭 | 默认要快到能用;出问题一键回退 |
| K154 | 是否动磁盘格式 | **不动** | 补丁不该带迁移;所有收益来自内存结构与协议 |
| K155 | 门限是否分档 | 分"必须达到"与"记录值"两档 | 并行度受机器核数影响,只对单线程可复现项设硬门限 |
| K156 | 本期是否顺手做 `EXPLAIN ANALYZE` | **不做** | 属 P8 功能项,避免与性能补丁混在一起验收 |
